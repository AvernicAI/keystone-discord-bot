# Open-source prior art — 2026 refresh

## Repos that matter

| Repo | Stack | Architecture idea | Failure to avoid |
| --- | --- | --- | --- |
| [Red-DiscordBot](https://github.com/Cog-Creators/Red-DiscordBot) | Python / discord.py | Cogs as a feature registry; in-Discord install; approved-spec gate | Hot-loading arbitrary third-party code |
| [YAGPDB](https://github.com/botlabs-gg/yagpdb) | Go / Postgres / Redis | Separate bot, web and feed plugins; web panel is a first-class process | Heavy self-host prerequisites as the default |
| [TSCord](https://github.com/barthofu/tscord) | TypeScript | Guards as declarative middleware; migrations; CLI scaffolding | Template stalled; DI ceremony |
| [MASZ](https://github.com/zaanposni/discord-masz) | C# + Svelte | Bot + dashboard + REST API + plugins | Maintainer abandonment with no succession |
| [Skyra](https://github.com/skyra-project/skyra) | TypeScript | Typed i18n and command design | README discourages self-hosting |
| [NadekoBot](https://github.com/nadeko-bot/nadekobot) | C# | Classic all-in-one feature set | CLA assigns copyright for relicensing |
| [Auttaja](https://github.com/Auttaja-OpenSource) | Go / Kubernetes | Distributed shard manager | Over-engineered for anyone else to run; dead since 2019 |
| [iHorizon](https://github.com/ihrz/ihrz) | TypeScript / Bun | 390+ commands, Lavalink, backup, 10 locales | Canonical repo on GitLab; GitHub issues disabled |

## Three ideas worth copying

1. **Red's registry, not switch.** A feature is a folder that declares itself;
   the host validates and loads it. Keystone already has this; the next step is a
   generator and an import-boundary lint, not a plugin marketplace.
2. **YAGPDB's process split.** The dashboard is not bolted on later; it is a
   deployment target that can fail without taking the gateway down. Keystone's
   `apps/bot` + `apps/worker` + later `apps/web` is the same idea at a smaller
   scale.
3. **TSCord's guards.** Cross-cutting policy (guild-only, permissions, cooldowns)
   is middleware, not repeated inside every command. Keystone's kernel guards are
   the implementation.

## Three failure modes

1. **Abandonment without succession.** MASZ's README asks for a maintainer;
   Auttaja's org has no public members. A bus factor of one is an architecture
   problem. Keystone answers with docs, a generator, CI and a governance ladder.
2. **Operational heaviness as a substitute for product decisions.** YAGPDB needs
   Postgres, Redis, TLS and three process roles; Skyra needs InfluxDB, Postgres
   and many API keys. A self-hosted bot that needs a platform team loses the
   audience the licence was meant to empower.
3. **Hostile contribution paths.** Skyra tells users not to self-host; Nadeko
   requires a copyright-assigning CLA; iHorizon disables GitHub issues. Keystone
   uses a DCO, a public roadmap and a spec-first contribution path.

## What this means for the plan

- Keep the modular monolith and four processes; do not add Kubernetes.
- Keep the DCO and no CLA.
- Add `pnpm module:new` and import-boundary lint in P7, not a marketplace.
- Make the dashboard optional in compose so a gateway-only self-host stays small.
- Treat "self-host in one command" as a launch gate, not a README claim.

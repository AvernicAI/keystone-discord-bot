# Pass 37 — The join gate is a state machine, not a button

**Date:** 2026-11-01
**Phase:** P7
**Tree before:** `b94af18` (clean) · 17 roots / 117 subcommands / 134 actions / 4 context menus / 371 tests
**Tree after:** this pass · same ledger · 385 tests / 58 files

## The hole pass 36 left

Pass 36 made `/verify` a real hub and made `status` read the `members` table, but
nothing ever wrote the state it read. `SecurityCoordinator` removed the
quarantine role and opened a case; it did not persist a held row. The only
writers were the completion path and a test fixture. Two consequences:

1. `start` refused only when a record existed and was not quarantined. With no
   record at all it proceeded to the DM, so any member could ask for the button.
2. `completeVerification` checked `verifiedAt`, not `quarantined`. A button click
   with no record (or a record from another flow) could reach `unquarantine` and
   then stamp `verified_at` for someone who was never held.

That is not a missing nicety; it is a bypass of the exact prerequisite `/verify
start` was introduced to check. `Object.prototype`-style truthiness made it look
covered because the happy-path test wrote its own fixture row.

## The four states

| State | Reached by | `start` | `status` | `completeVerification` |
| --- | --- | --- | --- | --- |
| no record | member never seen with the gate on | refusal, no DM | `No verification record` + `Ask a moderator`; no dead-end start | refusal, no action |
| quarantined | enforced `join-gate.*` hold writes the row | one DM with the existing button; row unchanged | `Quarantined; verification is not complete` + `/verify start` | allowed transition after `unquarantine` |
| verified | completion stamped `verified_at` | refusal: already verified | `Verified at …` | refusal: already verified |
| gate disabled | operator turned the gate off | refusal before state | state + `join gate is disabled here`; no start step | refusal before state |

The gate check comes first in both commands. A member with no record is told that
no quarantine is recorded, not sent a button that could never complete.

## What changed

- `packages/kernel/src/types.ts` — `MemberStore.markQuarantined(guildId,
  userId)` joins `get` and `markVerified`. One port, three operations.
- `modules/moderation/src/members.ts` — the in-memory upsert. It preserves the
  original `joinedAt`, sets `quarantined: true`, clears `verifiedAt` and returns
  a copy, exactly like the SQL adapter.
- `packages/db/src/member-store.ts` — the same upsert on the existing `members`
  table through `onConflictDoUpdate`. No new table, no migration: the row already
  had every column this pass needs.
- `modules/moderation/src/security.ts` — `SecurityCoordinator` now takes a
  `MemberStore`. In `#act`, a successful `quarantine` whose rule starts with
  `join-gate.` calls `markQuarantined`. The order is deliberate: no row before
  the role action succeeds, and no row for anti-raid/anti-nuke holds, which are
  moderator actions rather than a verification queue. The verify button is
  attached only to `join-gate.*` quarantine notifications.
- `modules/moderation/src/verification.ts` — `completeVerification` refuses no
  record and any row where `quarantined` is false, before it touches Discord.
- `modules/moderation/src/commands/verify.ts` — `start` refuses no record, a
  disabled gate and an already-verified row, then sends the DM. `status` has an
  explicit view for each of the four states and does not offer `/verify start`
  when no hold exists.
- `apps/bot/src/runtime.ts` — passes the existing `memberStore` into the
  coordinator. No new store instance.

## The cross-check

The reported state and the stored row were checked against each other, not just
against the command text:

- `verification.test.ts` calls `members.get` **before** completion and asserts it
  is undefined, then after a successful transition asserts the same port returns
  `{ quarantined: false, verifiedAt: "2026-11-01T00:00:00.000Z" }`. A failed
  action still returns `{ quarantined: true, verifiedAt: undefined }`.
- `security.test.ts` asserts the join write in the same `InMemoryMemberStore`
  that the command reads: the young account is `quarantined: true`; the
  old-enough account is `undefined`; the dry run leaves `joiner-0` undefined.
- `packages/db/src/member-store.test.ts` reads the PGlite `members` row directly
  after `markQuarantined` — one row, `quarantined: true`, `verifiedAt: null`,
  and the original `joined_at` preserved after a second write.
- Live, the command and the store agreed in the negative direction:
  `!verify status` said `No verification record`, and the MCP run wrote no row.

## What the MCP could not do

The MCP account is a bot:

- It cannot make a member join the guild, so the `GuildMemberAdd` → coordinator
  → `markQuarantined` path was **not** run live. `security.test.ts` drives the
  same structural event the adapter produces.
- It cannot receive a DM from another bot or click a message button, so
  `completeVerification` was **not** run live. `verification.test.ts` covers all
  four states and both failure orders.
- It cannot create a fresh account below the age threshold, so the live join
  case is not reproducible with this account even if a second client joined.

No live transcript in this page claims a join, a DM or a verification. Those are
test evidence only.

## What we tried and rejected

- **Write `markQuarantined` on every `member.join` when the gate is enabled.**
  Rejected: an account above the age threshold is never quarantined, so the row
  would be a hold that does not exist. The write belongs after the enforced
  action, not after the event.
- **Write the row before `actions.quarantine`.** Rejected: a failed role grant
  would then leave a `quarantined` row and a `/verify start` that sends a button
  for a role the member does not have. State follows the successful action.
- **Record anti-raid holds in `members` too.** Rejected: anti-raid is a bulk
  moderator action, not an individual verification queue; it already gets a case
  and a notification. Including it would attach a verify button to a hold the
  moderator did not create for verification. Both the write and the button are
  limited to `join-gate.*`.
- **Let `completeVerification` create a row when none exists.** Rejected: that is
  the original bypass in a different place. No record means no hold, and the
  honest answer is a refusal.
- **Use the case state as the verification state.** Rejected: cases are
  accountability records that survive a role change; verification is a member
  lifecycle flag. Two different lifetimes deserve two rows, and the `members`
  row already existed.
- **Add a `quarantined_at` column / migration.** Deferred: no command reads it
  yet, and adding a column would require a migration for no proven behaviour.
  The teaching note records it as the next extension, not as shipped.
- **Let `status` infer quarantine from the Discord role.** Rejected in pass 36
  and still rejected: a role rename or manual grant would change the answer
  without a row changing.

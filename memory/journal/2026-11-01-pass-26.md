# Pass 26 — the command tree becomes real

**Date:** 2026-11-01 · **Phase:** P7 · **Branch:** main

## Why this pass

The user saw **11 commands** after re-inviting the bot and granting the
`applications.commands` scope. Those 11 were real, correctly registered roots;
the problem was underneath them. The kernel spoke a flat `action` option, so
`/mod ban`, `/rank daily` and `/tools giveaway` existed only as hidden choices
inside one option. Discord's picker had nothing to expand.

This pass makes the tree real. It does **not** invent commands for features that
do not exist yet. The approved 18-root plan is the target; this pass migrates
every hub that already has behaviour, so the 77 working actions are visible in
Discord instead of hidden behind a text option.

## What changed

- `packages/kernel` now models `subcommands` and `subcommand groups`, validates
  them against Discord's limits, dispatches the selected path, exposes the path
  to commands as `ctx.commandPath`, and copies it into the structural
  `InteractionLike`.
- `/mod` (14), `/rank` (12), `/ticket` (8), `/tools` (24), `/ai` (11) and
  `/invites` (3) are true subcommand hubs. No command root was added for a
  feature that did not already ship.
- `/help` is new: `browse`, `commands`, `search`, `privacy` and `changelog`.
  Its catalog is injected from the live registry, so it cannot advertise a
  command that Discord did not receive.
- The development `!` bridge understands `!mod history` and
  `!help search query=ban`, and still runs the real registry, guards, cooldowns
  and reply adapter.
- `pnpm commands:catalog` writes `memory/machine/commands.json` and
  `memory/vault/01-Mission/Command-Catalog.md` from the registry. There is no
  hand-maintained command list in the docs.
- `pnpm commands:doctor` is read-only. It prints the application, guilds,
  registry shape, live Discord shape and any missing/extra/changed root, plus the
  exact `bot applications.commands` invite URL. It never prints the token.

### Two defects found while proving it

1. **The adapter dropped subcommand arguments.** Discord nests a subcommand's
   options inside `interaction.options.data`; `asInteractionLike` flattened only
   the top level, producing `{ ban: null }` instead of `{ user, reason }`. A real
   slash `/mod ban` would have failed even though the prefix bridge passed. The
   adapter now walks the tree and a regression test covers the nested payload.
2. **Boot sync compared names only.** After a payload change that keeps root
   names, the bot believed Discord was current and never re-registered the new
   subcommands. `command-sync.ts` now produces a canonical name + description +
   option-tree shape; boot sync, `commands:sync` and `commands:doctor` share it.
   Empty `options: []` is normalised away because Discord omits it.

## What we tried and rejected

- **Add 18 roots now, including empty ones.** Rejected: an empty `/logging` or
  `/music` would advertise a feature that does not exist, spend a command slot,
  and make `/help` lie. Roots land with their modules.
- **Keep the flat `action` option and only rename it.** Rejected: Discord's
  picker cannot show choices as subcommands, and the user explicitly wants the
  real slash surface.
- **Clear and re-register on every boot.** Rejected again: Discord allows two
  global bulk overwrites per ten minutes, and a clear followed by a rate-limited
  register leaves the app with no commands. Drift detection is the safe path.
- **Hand-write the catalog page.** Rejected: it would drift from the registry on
  the next command change. The page says “generated” and is produced by a script.
- **Treat the doctor's “changed” roots as real drift.** The first comparison
  flagged five roots because our payload serialised empty `options: []` and
  Discord omitted the field. Diffing one root found the normalisation issue; the
  fix was in the comparator, not a blind resync.

The MCP is a message client. Its tool list exposes `send_message`,
`read_messages`, `search_messages` and channel/member management, but no
application-command or interaction invocation. The **Use Slash Command** install
permission the user granted applies to the MCP account inside the Discord client;
it does not add an MCP API method, and a bot token cannot create another app's
interaction. Slash `InteractionCreate` from a human client is therefore still the
one unobserved surface; the registration shape, the adapter payload and the same
dispatch path are now covered, and the doctor proves Discord received all 77
subcommands.

# Pass 73 — event panels, one reminder and a calendar

**Date:** 2026-11-05
**Phase:** P7.5
**Type:** product slice in the events module, its adapter and one migration.

## Why

An event could be created, opened, listed and answered with `/event rsvp`, and
`/event remind` could post a manual message. What a member never got was the
thing a Discord event is for: an announcement they can answer where they see it.
The only reminder was one a moderator remembered to send, and the export a
calendar could not read.

The gap register called this `gap.event-panels` and had named the same three
pieces since pass 69: buttons, a reminder the bot sends itself, and ICS. They
share one source — the `event_rsvps` rows — so building them apart would have
produced three answers to "who is coming".

## What changed

### Buttons call the existing service, not a second one

`/event edit state:open` now posts a public panel: the event's time, place and
counts from the same rows `/event list` reads, plus **Going** and **Not going**
buttons. The ids are signed, expiring ids minted by `buildEventPanel`
(`modules/events/src/panel.ts`) through the kernel panel signer, and routed by
the shared component router (`apps/bot/src/event-interactions.ts`).

Both handlers call `EventService.rsvp` — the exact method `/event rsvp` calls.
That is the design decision that matters: capacity, the open-state gate and
"one member, one row" stay in one place. The button cannot grant a seat the
command would refuse, and the refusal copy is the service's.

The panel TTL follows the event: it ends 24 hours after the event's end (or
start when no end is set), with an hour floor and a ten-year ceiling. A pinned
announcement should outlive a form modal's fifteen minutes, but a forgotten
panel from a past event must eventually stop accepting presses. The service's
state check is still the real gate.

### One reminder, fired by the tick that already exists

Nothing new schedules. The community module's 60-second `setInterval` already
sweeps giveaways, birthdays, feeds and stat channels; it now also calls
`EventReminderService.sweep` for the guild (`modules/events/src/reminders.ts`,
wired in `apps/bot/src/community-events.ts`).

The event row is the durable schedule: `starts_at`, the new
`reminderLeadMinutes` setting (5–10080, default 60) and `reminded_at`. A restart
reruns the same decision instead of losing an in-memory timer.

The idempotency guard is `claimReminder`: one conditional `UPDATE … WHERE
state = 'open' AND reminded_at IS NULL` increments the counter and returns the
row; only one overlapping tick can win. If the channel post fails, the claim is
released so the next tick retries rather than silently consuming the reminder.
The sender is recorded as `SCHEDULED_REMINDER_ACTOR` (`"system"`), which
`/event edit` renders as prose instead of an empty mention.

A reminder needs an audience, and a tick has no interaction to reply to.
Opening an event (and a manual `/event remind`) records the invoking channel on
the event row as `panel_channel_id` — migration 0021, one nullable column. A
second table keyed by event id would be a second source of truth for an event's
audience and would drift when the event was reopened elsewhere. Events opened
before this pass have no channel and therefore get no automatic reminder, which
is honest: the bot does not guess a channel to post in.

### ICS from the exact JSON payload

`/event export` still attaches the checksummed `keystone.events` JSON. It now
attaches a second file, built by `buildEventCalendar` from the same
`EventExport` object — not by reading the store again:

- one `VEVENT` per event, `UID:<id>@keystone`, `DTSTART`/`DTEND` in UTC;
- a missing end becomes one hour, because calendars need a `DTEND` and a longer
  guess would invent a plan the operator never made;
- one `ATTENDEE` per RSVP row, `PARTSTAT=ACCEPTED`/`DECLINED`, addressed as
  `urn:discord:user:<id>` because a snowflake is not an email and inventing one
  would be a lie;
- `X-KEYSTONE-*` fields carry the key, state and both counts for a reader that
  wants them;
- the four reserved characters are escaped (backslash first) and lines are
  folded at 75 **octets**, not characters, so a German description or an emoji
  stays valid.

There is no ICS checksum: the JSON carries it over the normalized payload, and
the calendar is derived from that payload in the same reply.

### Surface and storage

No new root and no new subcommand. The budget stays **20/100 roots · 141
subcommands · 161 actions · 4 context menus**. The surface grew by behaviour,
not by names: `export` keeps its one option and now returns two files, and
`edit` posts a panel when its state becomes `open`.

## What is proven, and what is not

**Proven by tests:** the service and router paths, the panel's copy and ids,
the claim/release bookkeeping against real SQL in PGlite, the ICS text, and the
adapter's post through a fake discord.js channel.

**Not proven:** a human button press on a real message (`InteractionCreate` is
outside the MCP surface), a real calendar application importing the `.ics`, and
one automatic reminder delivered to a live guild. Those are adapter-tested, not
live. The pass-41 bridge transcript below still describes the command path; no
new live run was attempted in this pass.

## What we tried and rejected

- **A second scheduler or a BullMQ delayed job per event.** Tempting because
  pass 45 already ships a delayed queue, but the community tick runs anyway and
  the event row is already the schedule. A queue job would need rescheduling on
  every edit and would duplicate the claim rule.
- **A `maybe` answer.** Three buttons and a third state is more product than the
  request; `going`/`not_going` already frees a seat on a decline, and `maybe`
  would make capacity ambiguous.
- **A new `/event panel` subcommand.** The root is at seven of Discord's 25, so
  it would fit, but opening an event is the moment an announcement is wanted.
  A second command would let an operator open an event with no panel and then
  have to remember another step.
- **A separate `event_panels` table.** One nullable column on the event row
  survives edits, deletes and reopens through the existing cascade; a second
  record would drift.
- **Reading RSVPs again inside the ICS builder.** Two reads in one command can
  disagree under load. The serializer takes the export payload it is given.
- **Hashing the ICS too.** JSON needs its checksum inside itself; the calendar
  is a derived view of the payload that checksum already covers.
- **Deleting the manual `/event remind`.** A moderator may want to remind
  outside the lead window, and the pass-41 live record proves that path. The
  automatic reminder adds a path rather than replacing one.
- **Posting a reminder into a default channel.** The bot has no defensible way
  to pick one; recording the announcement channel is the only honest source.

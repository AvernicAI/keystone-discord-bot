# Pass 76 — one member timeline behind `/mod history user:`

**Date:** 2026-11-05
**Phase:** P7.5
**Branch:** `feat/member-timeline`

## What changed

`/mod history user:@member` used to be a list of that member's cases. It is now
one Components V2 timeline that answers the question a moderator actually asks:
*what has this member done and what have we done to them?*

The command still owns no new persistence. `MemberTimelineService` reads the
ports the command already receives:

| Source | Rows | What it contributes |
| --- | --- | --- |
| `cases` | up to 8 | case number, action, state, reason |
| `case_events` | every event on those cases | notes, reviews, appeals, expiries |
| `tickets` | up to 8 | subject, state, opening and closing time |
| `levels` | one | level, XP and rank in the top 100 |
| `economy_ledger` | up to 8 | signed amount and reason |
| `invite_joins` | one join and optional leave | inviter, code, join/leave time |
| `form_submissions` | up to 8 | form name, state, submission time |
| `event_rsvps` | up to 8 events | going/not going and the event name |
| `modmail_threads` | up to 8 | subject, state, message count, close time |
| `members` | one | joined, verified, quarantined |

The resolved rows are sorted newest first and capped at 12, with the number of
older rows stated below them. The header carries the facts that are not events:
level, XP, rank, balance, inviter, retained invites, open case/ticket/modmail
counts, quarantine and verification state.

Every row is suffixed with the source name in backticks. That is the point of
the pass: a reader can tell a ticket from a case event without opening another
screen.

## Honest failure is part of the design

A store can be absent or throw. Neither case is rendered as "no activity":

- `not-wired` means the composition root did not hand the command that port.
- `failed` means the port was called and threw.
- `ok` with zero rows is the only state that means "nothing recorded".

The cases read is split from the per-case event read, so a failure to count open
cases cannot discard the case rows already read. The open counts are capped by
the same read limit and rendered with `+` at the cap rather than pretending to be
exact.

Messages authored by members (case reasons, ticket subjects, form names, modmail
subjects) pass through one `clean` function that collapses whitespace, caps
length and neutralises `@everyone`, `@here` and user mentions. A reason cannot
ping the channel from a private history panel.

## What deliberately did not join

- **Logging events** have no member index. Scanning the whole ledger to find a
  member would be a different feature and a different cost; the footer says so.
- **AI labels** are advisory and not a moderation record; they are named as not
  joined instead of being presented as fact.
- **Voice, message counts and per-channel activity** are not stored per member
  in this build.

## Command surface

No root, subcommand, option, action or table was added. `history` already had a
`user` option and a `format` option:

- `format:json|csv` keeps the existing checksummed case export; it is checked
  before the panel branch, so an export is not silently replaced by a panel.
- `user` without `format` renders the timeline.
- no `user` keeps the compact recent-case embed.

## What we tried and rejected

**A new `member_timeline` table.** Rejected. The timeline is a projection over
rows that already exist. A table would need a write on every case, ticket, XP,
ledger, invite, form, RSVP and modmail transition, and it would immediately be a
second source of truth that can disagree with the first. The read model is
allowed to be slower because a moderator asks it once.

**One SQL union across nine tables.** Rejected for this pass. The command runs in
both Postgres and memory mode, and the ports do not share a query language. A
hand-written SQL union would either live in the module (forbidden: modules may
not import Drizzle) or duplicate the ports for one screen. Reading through the
existing ports keeps one contract and makes the failure isolation testable.

**Throwing when a store is unavailable.** Rejected. One missing port would blank
the whole history, including the cases that are the reason the panel was opened.
The footer names the missing source instead.

**Rendering a failed source as "no activity".** Rejected. Those two states have
different meanings to a moderator deciding whether to trust the screen.

**Paginating the timeline.** Rejected for this pass. Discord panels cannot page
without state or a signed cursor, and a history query is not a feed. The cap and
the explicit older-row count are the smallest honest version. A follow-up can add
a signed "older" control when a real workflow asks for it.

**A new `/history` root.** Rejected. The command budget is a gate, `history` is
already a `/mod` subcommand, and the existing `user` option is the natural
selector. A root would cost a global slot and split moderation reads.

**Replacing the case export.** Rejected. `format:json|csv` is a checksummed,
portable record; a V2 panel is a screen. The export branch stays first and the
panel is the no-format path.

**Including raw log lines.** Rejected for this pass. Logging has no member index;
a scan would be unbounded and would mix operator audit events with member
activity. The footer states the omission rather than hiding it.

## Live proof

The timeline itself is **not claimed live**. This session's Discord MCP is in
write-preview mode (`WRITE_PREVIEW`: `MCP_WRITE_MODE` is not `allow`), so the
harness could read the guild but could not post `!mod history user:@member`.
The browser preview was signed out, so it was not a human client either.

What the MCP did prove, read-only:

- `users_get_current` returned **AllTheMons GPT** (`1493685079468146808`), the
  MCP account, not the Keystone bot.
- `users_list_current_user_guilds` returned **Mr Bubba's server**
  (`1450130465146142785`).
- `channels_list` returned 7 channels, including `#general` and `#ai-chat`.
- `members_list` returned 3 members: Mr Bubba, AllTheMons GPT and **AI Team**
  (`1549086192794992710`), the running Keystone application.

The first `pnpm commands:doctor` read the live application as **AllinOne**
(`1549086192794992710`): 20 roots, 141 subcommands and 4 menus registered, with
`/mod` reported as drifted. The drift **was** caused by this pass: the
subcommand description changed from “List or export recent cases” to “List
cases, or open a member's full timeline across modules”. The two stale bot
processes were stopped; one fresh boot detected the drift, cleared once,
re-registered 24 commands and logged `commands re-registered`. A second doctor
run is clean (no `Changed` line), so Discord now carries the new description.
That is registration proof, not an invocation: the panel itself was not posted.

So the panel is proven by the command and panel tests, the registration is
proven by the doctor, and a real Discord invocation plus a live cross-store read
remain open. They are named in `Status.md`, `passes.json` and the feature row.

# Pass 30 — `/config`, one settings path for every module

**Date:** 2026-11-01
**Phase:** P7
**Commit:** pending at the time of writing

## The gap

The registry held 14 roots with 90 subcommands. The approved 18-root plan still
lists `/config`, `/export`, `/music` and later-domain roots. `/config` was the
highest-leverage missing root: every module already has a Zod settings schema and
`SettingsService` already validates reads and writes for the dashboard, but a
guild admin inside Discord could only change settings by opening the web
dashboard or asking another module's bespoke command. `/config` exposes the same
service to the surface most operators actually use, and it does not create a
parallel settings store.

`/export` was rejected for this pass because P5 already ships the full bundle
through the portability CLI and the dashboard, and a second export surface would
invite divergence before the first has a UI. `/music` was rejected because it
needs a BYO Lavalink node and cannot be exercised honestly from this machine.

## What changed

One root, four real subcommands:

| Subcommand | Options | Behaviour |
| --- | --- | --- |
| `/config list` | none | Every registered module, its enabled state and its effective key count |
| `/config get` | `module`, optional `key` | One module's effective settings, or one dotted key |
| `/config set` | `module`, `key`, `value` | Parse the value, apply it as a dotted patch, validate the whole record through the owning module's Zod schema, then store it |
| `/config export` | none | Effective settings for every module as versioned JSON |

The command lives in `modules/setup`, which already owns the operator's first
questions. It is guild-only, requires `ManageGuild`, and has a two-second
cooldown applied at the root, so every subcommand is covered once. No new module,
no migration, no new table and no new setting concept.

### The seam

`packages/kernel/src/config.ts` defines the narrow `ConfigPort`:

```text
list(guildId)                       -> ConfigModuleView[]
get(guildId, moduleId)              -> effective settings
update(guildId, moduleId, patch)    -> validated effective settings
```

`SettingsService` implements it. The port exposes no repository, no raw table
and no environment value. The command never imports Drizzle, another module's
store or a Discord type. The only write is `settings.update`, which merges the
current record, parses it with the module's schema, and only then persists it.

Dotted keys are built by `patchFor`, which clones each object on the path rather
than mutating the current settings. Keys are restricted to
`[A-Za-z][A-Za-z0-9_-]*` segments and `__proto__`, `constructor` and `prototype`
are refused, so a crafted key cannot reach the prototype chain. Snowflake-shaped
values (`15–25` digits) are kept as strings before `JSON.parse`, because Discord
ids exceed `Number.MAX_SAFE_INTEGER`; a channel id rounded through a JS number
would be a silently wrong setting.

A schema failure is converted to a `UserError` with the failing path and message,
so the user sees `automod.links: Invalid enum value...` instead of the generic
dispatcher error.

## Live proof

Exactly one bot process. The configured services were probed first, not assumed:

```text
DATABASE_URL: localhost:5432 -> ECONNREFUSED (19ms)
REDIS_URL:    localhost:6379 -> ECONNREFUSED (1ms)

Booting without overrides reached `settings: postgres`, then failed loudly:

The pass therefore used the explicit memory-mode window documented since pass 27
(`DATABASE_URL= REDIS_URL= pnpm start`) and reports the configured endpoints as
unusable rather than claiming a live Postgres/Redis run.

```

The MCP author is an ordinary guild member with the install permissions; it
cannot invoke a slash command, so this transcript proves the registry, guard,
schema and reply adapter through the real gateway message path, not
`InteractionCreate`.

### Cross-check

The write is traceable without a new metric: after
`!config set ... value=delete`, `!config get ...` returned exactly
`"delete"` from `SettingsService.get`; after resetting to `alert`, the next read
returned `"alert"`. There is no cached copy and no second store to disagree. The
invalid `bogus` write returned the schema issue and the following read still
showed `"alert"`, proving the rejected value was never persisted.

`/config list` printed 8 modules and 1 disabled module; the 8 matches the
registry's module count and the disabled count comes from the same effective
settings the individual reads use. The MCP text reader does not render embeds,
so the list's per-module fields and the JSON export body were not read back
live; they are covered by the command test. A human slash run remains the one
unobserved surface for the picker and embed rendering.

## What we tried and rejected

- **A new `config` module.** Rejected: it would add a ninth module and a spec
  page for four thin commands, while the setup module already owns readiness and
  operator configuration. The root is what the plan asked for; the module
  boundary need not move.
- **A flat `/config set module key value` root with no subcommands.** Rejected:
  the plan and pass 26's ADR require real subcommands, and `list`/`get`/`set`/
  `export` are distinct actions with different argument shapes.
- **A JSON document patch for the whole module.** Rejected for this pass: a whole
  object is harder to type in Discord and makes a partial edit likely to drop
  unrelated keys. One dotted key is smaller and still goes through the full
  schema parse.
- **Exposing the settings repository to the command.** Rejected: it would bypass
  `SettingsService` and give a command the ability to write a raw row the schema
  never saw. The port only exposes the three operations the command needs.
- **Free-form `eval` of the value.** Rejected: `JSON.parse` plus a string
  fallback is enough for booleans, numbers, arrays and objects; arbitrary code
  execution in a chat command is unacceptable.
- **A config-template / bulk-apply surface.** Deferred to P6's fleet work; it
  needs an explicit preview and is not part of this root.

## Limits

- Memory mode resets settings on restart. That is the documented local mode, not
  a regression; the configured Postgres is still unreachable on this machine.
- The schema checks shape, not referents. `/config set` can store a channel id
  that no longer exists if the module's schema only requires a string; a
  referent check belongs to the module that owns the channel, not this command.
- There is no settings-change audit event yet. The value is visible through
  `/config get` and `/config export`; an append-only settings log would be a
  sensible next addition.
- `/config list` and `export` render embeds the MCP cannot read. The command
  test asserts their structure.

## Next

The next missing plan root is `/export` (surface the existing bundle above the
CLI) or `/music` (only with a BYO Lavalink node). Before either, the cheaper
hardening is a settings-change audit row so `/config set` leaves the same kind
of trace the moderation and logging paths already do.

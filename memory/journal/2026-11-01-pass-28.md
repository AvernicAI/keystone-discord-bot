# Pass 28 — audit logging

**Date:** 2026-11-01 · **Phase:** P7 · **Branch:** main

## Why this pass

The approved v1.0 plan names `/logging` as the next missing root: Dyno sells
multichannel logging and Carl-bot makes logging a headline feature, so an
all-in-one without it is visibly incomplete. It is also the event source the
later `/analytics` root needs; adding analytics before a retained event stream
would create a second collection path.

## What changed

- New `modules/logging` package: manifest, settings schema, five-event table,
  `LoggingService`, embed formatter, in-memory store, command and tests.
- `/logging setup | channel | events | status | retention | export | disable`
  under **one new root**. The ledger is now **13 roots · 84 subcommands · 97
  actions**.
- New `logging_events` table and `DrizzleLoggingStore`; migration `0009`.
  Append-only, indexed on `(guild_id, created_at)`, with one scoped prune.
- Gateway translation in `apps/bot/src/logging-events.ts` and delivery in
  `apps/bot/src/logging-actions.ts`. The Discord adapter does no policy.
- `CaseService` gained an optional `onOpened` observer. Moderation cases enter
  the same ledger without logging reading the cases table itself.
- Retention runs at startup, immediately after `/logging retention`, and every
  six hours.
- The shared dev marker seam now covers log events: a bot-authored message is
  captured only in `DEV_GUILD_ID` and only when it carries `keystone-test:`.
  The marker is stripped before storage; production passes no guild id.
- Web dashboard test fixture updated for the seventh registered module. No new
  web route or write path was added.

## What we tried and rejected

- **Log every message and filter later.** Rejected: an audit log should store
  only the events an operator enabled. Storing everything would make the
  retention promise and the privacy story false.
- **Deliver first, then store.** Rejected: a deleted channel would lose the
  event, which is the one case where an audit log matters most. The row is
  durable before the send.
- **A separate `/logs` root or a `/logging` mirror of every filter.** Rejected:
  Discord gives 100 global roots total; seven subcommands under one root cost
  nothing extra and keep `/logging status` as the single destination.
- **A background worker for retention.** Rejected for this pass: the bot already
  knows its guilds, and a six-hour timer plus startup prune is smaller than a
  BullMQ job that would need Redis to be useful. A worker job can be added when
  fleet scale makes the timer too coarse.
- **Recording the moderator who deleted a message.** Rejected: the gateway
  `MessageDelete` event does not name the executor. Reading Discord's audit log
  needs another permission and API surface. The event records the author and
  says so in the status page; it does not invent an actor.
- **Reading message content for every event.** Rejected: only delete and edit
  need content that Discord will otherwise lose. Keeping it for joins or cases
  would turn a logging module into a message archive with a different promise.
- **Calling the live proof a member proof.** Rejected: the MCP bot cannot join or
  leave a guild. Member join/leave are adapter-tested and explicitly listed as
  open.

  event, and confirm the ledger still has the row.
- Reuse `logging_events` for the `/analytics` aggregates rather than adding a
  second event table.

# Pass 21 — invite gateway boundary

**Date:** 2026-11-01
**Phase:** P7 architecture
**Commit:** pending (working tree)

## What changed

The invite gateway had one closure doing five jobs: holding the cache, owning the
per-guild promise chain, reading settings, calling the service and translating
discord.js events. That made the state impossible to exercise without a fake
gateway client, and it hid the serialization invariant inside event
registration.

The pass splits it at the boundary the domain already has:

- **`apps/bot/src/invite-tracker.ts`** is the gateway-independent owner. It holds
  the per-guild invite snapshots, the per-guild promise chain, the one-warning
  set and the join/leave decisions. It receives a normalized join profile and a
  `fetchInvites` closure, so it imports neither discord.js nor a gateway client.
- **`apps/bot/src/invite-events.ts`** is now a translation layer. It maps
  `GuildMemberAdd`, `GuildMemberRemove`, `InviteCreate`, `InviteDelete`,
  `ClientReady` and `GuildCreate` to tracker calls, and it maps discord.js
  invites to the kernel `InviteSource` shape.
- Error policy and logging moved with the state. A failed join/leave/fetch is
  logged by the tracker, which is the component that knows why it failed.
- `apps/bot/src/invite-tracker.test.ts` now proves the per-guild queue directly:
  two joins are issued, the first fetch is held open, the second join must not
  reach `recordJoin` until the first cache update lands, and then the second
  join records the incremented invite.

The cold-cache behavior is unchanged: no baseline means no attribution, and the
fresh fetch seeds the next join. Historical `uses` totals are never treated as
increments.

## Why this shape

The tracker is a real state machine, not a pass-through abstraction. It has
state (cache, queue, warned guilds), a reason to exist without Discord (tests and
future durable snapshots), and one caller that only maps events. The arrow points
one way: discord.js → `invite-events` → `invite-tracker` → `InviteService` →
`InviteStore`/`InviteActions`.

This also makes the serialization test honest. The old limitation said the
queue was “code-inspected”; after extracting it, the queue has a direct test
without a fake event emitter.

## What we tried and rejected

- **Keep the closure and only add a test seam.** Rejected: the seam would still
  be the event adapter, so the cache owner would remain implicit and the test
  would not explain where state lives.
- **Move the tracker into `modules/invites`.** Rejected for now: it still needs a
  fetch closure and a log consumer, which are gateway composition concerns. The
  module already owns the pure diff and the service; the tracker sits at the
  boundary between them.
- **Serialize `refresh` through the same per-guild chain.** Rejected: that would
  change boot behavior and let a slow ready-time fetch delay joins. The existing
  refresh is independent; the cache read/write remains guarded by the join queue.
- **Split the dashboard server in the same pass.** Rejected as out of scope. The
  changed surface is the invite gateway; the dashboard already has its own
  security contract and is not re-shaped by this pass.
- **Add a new invite feature or command.** None. This pass changes structure and
  preserves behavior.

## Limits

- A real `GuildMemberAdd` was still not observed; the tracker and adapter are
  proven with fakes, and the live run proves login, refresh and command dispatch.
- The cache is still process-local. A restart can leave the next join
  unattributed; the explicit no-baseline path is the honest answer.
- The queue test is deterministic but not a live Discord race. The unique SQL
  join key remains the idempotency backstop.
- The dashboard monolith is untouched; its structure is a separate pass.

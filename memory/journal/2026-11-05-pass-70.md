# Pass 70 — the Discord MCP proof surface

**Date:** 2026-11-05
**Phase:** P7.5 (truth)
**Type:** documentation and a read-only external check. No product behaviour changed.

## Why

The project grew on a dev-only `!` bridge because an external bot cannot invoke
another application's slash command. That fact lived in one short paragraph.
Meanwhile the configured `discord-mcp` server exposes 189 tools: enough to
create channels, roles, invites, webhooks, scheduled events, threads and V2
messages, and to read every one of them back. A pass could easily mistake that
reach for proof of an interaction. The boundary needed to be written down once,
with tool names, so a later pass cannot blur it.

## What changed

`memory/vault/03-Architecture/Live-Testing.md` gained a full section:

- **The nine tool groups** with representative names and what each proves:
  read state, outbound text, Components V2, structure, roles and members,
  invites and webhooks, scheduled events, threads and forums, server
  configuration.
- **What it proves well:** outbound replies as a closed send/read loop, V2
  validation before send, state changes confirmed by a second read, and
  scenario setup.
- **What it cannot prove:** `InteractionCreate` (no tool invokes a command,
  presses a button, picks a select or submits a modal), a member join (kick and
  ban remove; nothing adds), a DM with a human, voice audio, and a file upload
  (`messages_send` is text-only and File components are rejected because send
  does not upload).
- **The three proof classes** and their mapping to the pass-69 schema:
  `probe` → `liveScope: probe` + `liveEvidence`; `mcp` and `gateway` →
  `liveScope: manual` + a `liveRecord` that names which one. The record carries
  the distinction the enum deliberately does not.

The intro was corrected too. It said the MCP "has no application-command
method". It has `commands_create_guild`, which registers a guild command; what
it lacks is any way to invoke one. That is a different sentence and the old one
was wrong.

`AGENTS.md` now states the 189-tool surface and links the page, and its pass
protocol still says "never blur" probe, MCP and gateway.

## Verification

Read-only external check, 2026-11-05:

- `users_list_current_user_guilds` → **1 guild**, 3 members.
- `channels_list` on that guild → **7 channels**, including `#ai-chat` and
  `#keystone-logs`.

Those confirm the MCP is connected and reads real guild shape. They are not a
gateway proof and no feature row was changed to `liveVerified` by this pass.

Repository checks: `pnpm memory:render && pnpm check` green; 631 tests in 92
files; budget 20/100 roots; claims 35/35; memory **4,855/4,855** (the count moves
with the new journal and pass row). `pnpm probe:live` was not rerun; the last
recorded probe is 28/28 on 2026-11-03.

## What we tried and rejected

- **Add `mcp` and `gateway` as `liveScope` values.** Tempting, but pass 69 just
  established the vocabulary and both are still "a human or external client did
  it and wrote it down". The record names which; a fourth enum value would
  imply a checker that cannot verify it.
- **Put the 189-tool inventory in `memory/machine/`.** The MCP server is
  external and versioned outside this repo. A machine file would go stale with
  no diff to warn anyone, and a gate cannot call the MCP. A dated page is the
  honest home.
- **Gate on the tool count.** The count is a fact about today's server, not a
  contract. A check would fail the moment the server adds a tool, which is not
  a defect in Keystone.
- **Prove a write with the MCP.** Tempting to send a message or grant a role for
  a stronger check. The old bridge proofs already cover outbound delivery, and a
  write would add destructive surface for no new knowledge. This pass stayed
  read-only.
- **Claim the MCP replaces a human.** It does not. It is excellent at setup and
  read-back and structurally unable to produce an interaction.

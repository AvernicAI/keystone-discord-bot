# Pass 75 — a help hub that knows this server

**Date:** 2026-11-05
**Phase:** P7.5
**Type:** diagnostics surface across a new facts loader, four pure panel
builders, four signed component routes and one bridge fix. No command, table or
migration.

## Why

The bot had 141 subcommands and a `/help` that printed an embed listing their
names. That answers "what exists", not "what does this server have, and what is
broken". An owner asking why tickets did not work had to run `/config`, `/mod`
and a health check separately; a member could see every operator command but not
which modules were on.

The interesting state already existed and was already injected into commands:
`ConfigPort`, `HealthProbe`, `CommunityPort`, `ModerationPort` and the live
catalog. The missing piece was a surface that joins them in one place without a
dashboard and without a second copy of the truth.

The visual layer could carry it. Components V2, `packages/ui` and the signed
component router shipped in passes 58–61; `/help` was one of the last member
surfaces still returning a plain embed.

## What changed

### Facts are gathered once, from ports the command already receives

`modules/diagnostics/src/help/facts.ts` turns five sources into one `HelpFacts`
object:

- settings → module display name and on/off state;
- health → database state, cache state and disabled features;
- community → open tickets, capped at 100 rows;
- moderation → open plus alerted cases, capped at 100 each, only when the caller
  has `ModerateMembers`;
- catalog → roots, subcommands and context menus.

Every optional source is allowed to fail. A settings failure leaves the module
ids and an unknown state; a health failure prints `unknown`; a ticket or case
failure omits that row. The command never becomes useless because one probe is
down. A count that fills the query limit prints `100+` instead of asserting a
total it cannot prove.

The facts loader is shared by the command and the component routes. A picker
update and the page that produced it therefore cannot disagree.

### Four pure trees, one page at a time

`modules/diagnostics/src/help/panel.ts` builds the home, module, privacy and
changelog pages through `packages/ui`. Nothing in it imports discord.js or calls
a service; every string comes from `packages/i18n`, including the new German
copy.

- **Home** shows the module summary, ticket and case counts (when visible),
  data/cache state, disabled features, the registry totals, a module picker and
  privacy/changelog buttons.
- **Module** shows each root with its subcommands, clips at 3,200 characters and
  names how many roots it left out instead of letting Discord reject the
  message. Its picker keeps every module, so switching pages does not require a
  trip through Overview first.
- **Privacy** and **changelog** reuse the existing copy, with an Overview
  button.

The home tree uses 9 of Discord's 40 components. `packages/ui` throws rather than
silently exceeding 4,000 characters; the module body has its own smaller budget
so the header and footer always fit.

### Controls are signed, and a DM is a different page

`apps/bot/src/help-interactions.ts` registers `help:browse` (select), `help:home`,
`help:privacy` and `help:changelog` (buttons) on the shared router. They are
`guildOnly` and carry a 15-minute TTL. Every update re-reads facts and mints a
fresh set of ids, so an old page expires on its own instead of pinning one id
forever.

A DM has no guild to bind an id to and no server state to show, so it keeps the
flat embed the command has always returned. `commands`, `search`, `privacy` and
`changelog` keep their text forms; an unknown module is refused by name before a
component is written.

### The development bridge stops flattening V2

`apps/bot/src/prefix.ts` used to rebuild a message body from content, embeds and
`toComponents()`. That was correct for the old component rows and wrong for a V2
tree: it dropped the `IsComponentsV2` flag and the typed container, so `!help`
would have shown the MCP a message that did not exist in the product.

The bridge now calls `toReplyOptions()` — the same adapter a slash reply uses —
removes only `ephemeral`, caps content and adds `allowedMentions`. An edit omits
the repeated flag because the message already carries it. The MCP can now read
the real panel through the bridge instead of a second renderer.

### The live boot found a registration bug

The first boot on this branch detected the passes 71–74 command drift, cleared
the old guild set and then failed to register: four German descriptions
(`/setup`, `/tools`, `/analytics`, `/modmail`) were 102–114 characters, over
Discord's 100-character limit. The clear had already happened, so the guild was
left with no application commands — exactly the failure mode AGENTS warns about.

The four strings are shortened, and a new test builds every chat-input command
and walks every localized description, failing if any exceeds 100 characters.
The next boot re-registered all 24 commands (20 roots and 4 context menus). The
bug predates this pass; the new hub only made the boot path visible again.

## What is proven, and what is not

**Proven by tests:** the facts join and its failure modes; every panel shape and
the character budget; the signed route path including expiry and the
permission-gated case count; the command's guild/DM split; and the bridge's V2
body.

**Not proven:** a human button press through the Discord gateway, and a live
read of the panel in a real channel. The live probe drives the command and the
route with real Postgres rows, but no Discord message was sent: the workspace
MCP is in `preview` write mode and its bot is not the running Keystone bot. It
cannot click a button even with writes enabled.

## What we tried and rejected

- **Reading the guild and its stores inside diagnostics.** It would couple a
  reference module to the gateway and duplicate ownership. The hub receives
  ports through the command context instead.
- **A single page listing every module's commands.** 141 subcommands do not fit
  in 4,000 characters, and a truncated list is worse than a picker. Module pages
  clip honestly and say what they left out.
- **An embed with fields instead of V2.** That is the surface this pass exists
  to replace; it also cannot carry a select.
- **Reusing the old `keystone:` ids.** Every other panel moved to signed,
  expiring ids in passes 58–64. A new panel with a legacy id would reintroduce
  the bypass.
- **A `/help hub` subcommand.** It spends a slot to reach the same page and
  splits the front door into two commands. `browse` already meant "show me the
  map".
- **Caching facts in the process.** Health and ticket counts are the point; a
  cached "ready" is the confident lie this project keeps deleting.
- **Letting the bridge keep its own renderer.** Two renderers means two shapes,
  and the MCP proof would describe the bridge rather than the product.
- **A new table or migration for help state.** There is no help state. The hub
  reads rows other modules own.

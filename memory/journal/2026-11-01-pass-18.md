# Pass 18 — P6 settings writes

## What changed

- Added the first P6 write path, reusing the existing authorization, session,
  CSRF and settings seams:
  - `PATCH /api/v1/guilds/:id/settings/:module` accepts a JSON settings object,
    checks the session CSRF header, authorizes the guild, and calls
    `SettingsService.update` with the module's own Zod schema.
  - `GET/POST /dashboard/guilds/:id/settings/:module` adds a server-rendered
    editor. The form carries the session CSRF token and saves through the same
    service. A successful save redirects back to the guild overview.
  - The guild overview links each registered module to its editor.
- `DashboardService.update` maps `ZodError` issues to a safe `400` and returns
  only the filtered, browser-safe settings view. Unknown modules are `404`.
- The form and API share the exact `GuildAccessService.authorize()` result; there
  is no web-only settings schema, guild id from the body, or direct repository
  write. Invalid input leaves the stored value untouched.
- Added `zod` to `apps/web` for the error type only; the validation itself remains
  the module's schema in `SettingsService`.
- Updated README, [[Dashboard]], [[ADR-0016-dashboard-foundation]], [[Roadmap]],
  [[01-Mission/Status|Status]], [[Home]], [[Decision-Log]] and feature status.
  The no-paid-services rule is unchanged.

## What we tried and rejected

- **A separate web settings allowlist or schema.** Rejected: the bot and
  dashboard would drift. `SettingsService.update` is the single validator and
  the shared module catalog is the single module list.
- **Schema-driven field widgets in this pass.** Deliberately deferred: the user
  asked for real existing settings, not new settings concepts. A validated JSON
  textarea covers every existing module without introducing a second schema;
  field widgets are the next UI step.
- **A PUT route that replaces the whole module record.** Rejected: it would
  bypass the existing patch semantics and make omitted fields ambiguous. The API
  forwards the object to `SettingsService.update`, which merges and validates.
- **Trusting the module or guild id in the body.** Rejected: both come from the
  path, the module must exist in the registry, and the guild comes from the
  authorized `DiscordGuild`.
- **Writing directly through `DrizzleSettingsRepository`.** Rejected: it would
  skip schema validation and duplicate the bot's path.
- **Skipping CSRF because the session cookie is HttpOnly.** Rejected: cookies are
  sent automatically; a JSON `PATCH` needs the explicit session-bound token.
- **Adding audit rows in this pass.** Not claimed: the existing audit table is a
  worker/portability seam and a dedicated audit port is a later decision.

The write proof is end to end through the real HTTP handler: a valid session and
CSRF token update AI settings through the API and the HTML form; the stored value
is read back through the same `SettingsService`. `monthlyBudgetUsd: 5000` returns
`400` with no mutation. Cross-guild, non-admin, bot-absent, unauthenticated and
missing-CSRF writes are rejected. No test needs Discord, Postgres or the network.

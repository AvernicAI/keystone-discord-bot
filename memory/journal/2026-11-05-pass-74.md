# Pass 74 — forms in the guild bundle

**Date:** 2026-11-05
**Phase:** P7.5
**Type:** portability slice across the importer, the SQL store, the memory export
port and the forms module's in-memory store. No command, table or migration.

## Why

`/form export` has shipped since pass 40: one form, its submissions and a
checksum, attached as `keystone.forms`. The whole-server bundle did not know the
two form tables, and the forms Spec listed that as a non-goal so nobody would
mistake the omission for an accident.

That made the exit guarantee false in the one place it matters. A server that
exported with `/export guild`, removed the bot and restored elsewhere got its
levels, cases, tickets and settings back — and lost every application and every
review decision. The record a moderator depends on travelled; the record an
applicant depends on did not.

The fix belongs in the existing bundle, not in a fourth exporter: one snapshot,
one checksum, one restore order.

## What changed

### The snapshot gained two arrays, and the version moved with the shape

`GuildSnapshot` now carries `forms` and `formSubmissions`
(`packages/importer/src/types.ts`). A form row keeps its id, key, name,
description, fields, state, panel channel, author and timestamps; a submission
keeps its id, form id, user, answers, state, reviewer, decision note and
timestamps. Ids are preserved rather than regenerated because
`form_submissions.form_id` is a real foreign key.

The manifest counts `forms`, `formSubmissions` and `formsUnique` (distinct keys)
beside the existing `casesUnique` and `levelsUnique`, and `INCLUDED` names the
forms in the file's own description of itself.

`EXPORT_VERSION` is now **2**. The version moves with the snapshot shape:

- A v1 file has no forms arrays. A v2 reader could have defaulted them to `[]`,
  and parsing would have succeeded — but a v1 bundle restores in `replace` mode,
  which deletes the destination's rows first. Defaulting would therefore have
  turned "this file predates forms" into "delete every form and answer on the
  destination", silently. Refusing by version forces a fresh export instead.
- The refusal already existed and names the readable version:
  `Bundle version 1 is not supported; this build reads version 2.`

No new code path was needed for integrity. The checksum is computed over the
whole snapshot, so the two arrays are covered automatically, and the manifest
count check runs before any write: an edited answer fails the checksum, and a
manifest edited to hide rows fails the count.

### Restore order, and the two adapters

`packages/db/src/portability-store.ts` reads both tables in the existing
`snapshot()` join, sorts forms by key and submissions by creation, and in
`replaceGuild` deletes submissions before forms and inserts forms before
submissions. The deletion order is not left to the cascade: the restore must
not depend on timing to empty a review queue.

The in-memory export port (`apps/bot/src/export-port.ts`) reads the same shape
through `allForms`/`allSubmissions` on `InMemoryFormStore`
(`modules/forms/src/store.ts`). Those are export-only accessors on the adapter,
not methods on `FormStore` — the same pattern `allLevels`, `allRecords`,
`allDocuments` and `records` already use in that port. `listForms` stays capped
because it answers a command; a snapshot must not silently drop the forms past a
cap. Pass 41 deleted a dead `allSubmissions`; it returns here with a caller.

`createRuntime` now passes the form store into `createMemoryExportPort` and
refuses to build a memory export port from a store that is not in memory, as it
already did for cases, community and AI.

### Merge still leaves forms alone

Merge is settings and levels by contract. A submission's pending-uniqueness rule
could also collide with an existing form key, and choosing a winner would be a
new policy. So merge keeps the current forms untouched — and its warning now
says so, where it previously named cases, tickets, ledger history and audit
events but not forms.

## What is proven, and what is not

**Proven by tests:** the SQL export/import round trip on PGlite including ids,
field definitions, answer sets and review decisions; the v1 refusal; checksum
and count enforcement over the new arrays; the in-memory port's counts.

**Not proven:** a live Postgres export and restore, and a real Discord download
of the bundle. The PGlite path is the same runner the portability suite uses,
but it is not the compose Postgres. No new live claim is made.

## What we tried and rejected

- **Defaulting the new arrays so v1 files still parse.** Cheap and wrong: the
  first v1 bundle restored with `replace` would delete every form on the target.
  A named refusal is one export away from solved.
- **A second file inside the bundle** (`manifest.formsFile`) so v1 could stay
  readable. It doubles the attachments, introduces a second checksum whose
  relationship to the first is undefined, and still cannot express "keep the
  destination's forms".
- **Reusing `/form export`'s `keystone.forms` payload verbatim.** That file has
  its own envelope, counts and checksum; nesting it would put a second format
  inside the snapshot and make one checksum cover a string rather than rows.
- **New `FormStore` methods for the export.** The port answers commands and
  enforces invariants; an uncapped dump is an adapter concern. The SQL side
  reads tables and the memory side uses accessors, as every other module in this
  port already does.
- **Regenerating form ids on restore.** It would silently orphan
  `form_submissions.form_id`; preserving ids is what makes definitions-first
  insertion meaningful.
- **Merging forms in merge mode.** It needs a key-conflict policy, a
  pending-submission rule across two rows and a decision about what happens to a
  reviewed answer with the same id. Replace-only is the smaller honest contract.
- **A fourth exporter command.** The bundle is the server's exit path; adding a
  command would spend a subcommand to hand the operator two files that must then
  be kept in step.

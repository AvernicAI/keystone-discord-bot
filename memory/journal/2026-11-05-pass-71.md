# Pass 71 — role persistence across leave and rejoin

**Date:** 2026-11-05
**Phase:** P7.5
**Type:** product slice in the community module.

## Why

Role persistence was the highest-priority open gap in the register and the one
generalist feature Keystone still lacked. Carl-bot sells it on premium; Arcane
and Lurkr do not document it. The promise is small and concrete: a member who
leaves should not have to rebuild their roles by hand when they come back.

The MCP cannot make a human join, so the honest ceiling for this pass is a real
adapter test that emits `GuildMemberRemove` and `GuildMemberAdd`. A human
leave/rejoin stays on the live checklist.

## What changed

### A service, not a branch

`modules/community/src/role-persistence.ts` owns the whole behaviour:

- `save(guildId, userId, roleIds)` writes one `community_records` row of kind
  `role_snapshot`, deduped and capped by `roles.persistMax` (default 20).
- `restore(guildId, userId)` adds each stored role once, counts refusals, then
  deletes the snapshot.
- `snapshot()` is read-only, for tests and diagnosis.

Separating it from `WelcomeService` matters: a server may want role persistence
with no welcome message, and the goodbye send must not be able to lose the
snapshot. The adapter takes the snapshot first, in its own `try`, then sends the
goodbye. A failing channel costs the message, not the roles.

### Discord is the authority

The service never decides that a role is safe to grant. It calls
`CommunityActions.addRole`, and Discord refuses a managed role, a role above the
bot, or a deleted role. The refusal is counted and reported; the snapshot is
still consumed, so a permanently invalid role cannot cause an infinite retry on
every join. No permission is escalated locally.

### Configuration without a new root or subcommand

Discord caps a command at 25 subcommands and `/tools` already had 25. A sixth
role option is the smallest surface that fits:

```text
/tools roles persist:on  limit:20
/tools roles persist:off
```

Choosing `persist` skips the panel path and writes `roles.persist` /
`roles.persistMax` through the module's own settings service. Without it,
`/tools roles` behaves exactly as before.

### Wiring

`apps/bot/src/community-events.ts` now creates a `RolePersistenceService` on
member join and leave. The join path runs after welcome, so an autorole and a
restore do not fight. A restore that changed anything writes one structured log
line with guild, user, restored and failed counts — the audit trail this slice
can honestly offer. A live join/leave is still not claimed.

## Verification

- New `role-persistence.test.ts` (4 tests): disabled mode writes and restores
  nothing; dedupe and cap; one-shot restore with snapshot deletion; a refused
  role counted while the snapshot is consumed.
- `commands.test.ts` gains the configuration path: `persist:on limit:12` writes
  both settings.
- `community-events.test.ts` gains the gateway seam: leave stores two roles,
  join calls `addRole` twice and deletes the snapshot.
- Focused runs pass; full gate green with **637 tests in 93 files**. Budget
  stays **20/100 roots, 141 subcommands** because the option replaces no
  subcommand and adds none.

## What we tried and rejected

- **A new `/tools role-persistence` subcommand.** Discord rejects a 26th
  subcommand; the registry test caught it before any memory was written. The
  limit is real, not a style preference.
- **A new `/roles` root.** It would fit the 100-root budget, but one toggle does
  not justify a new top-level command and a new permission surface.
- **Reusing `/tools welcome`.** Welcome is a message flow. Role persistence has
  to work with welcome disabled, and its cap is a different concept from the
  autorole delay.
- **Filtering by role hierarchy in the service.** It would duplicate Discord's
  own check and need a role cache the module contract does not expose. The API
  refusal is the correct authority; the cost is a failed count.
- **Keeping the snapshot after a failed restore.** A managed role would retry
  forever. One attempt, a reported failure and a clean row is the honest
  default; an operator can turn it off.
- **A DM on restore.** It is unsolicited and the member just arrived; the log
  line is enough.

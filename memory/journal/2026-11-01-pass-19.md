# Pass 19 — invite tracking (P7 slice)

**Date:** 2026-11-01
**Phase:** P7 (first slice)
**Commit:** `feat(invites): add invite attribution, leaderboard and advisory flags`

## What changed

A sixth module, `@keystone/module-invites`:

- **Attribution.** The bot caches `code → {uses, inviterId}` on ready, on
  `GuildCreate`, and on invite create/delete. After each `GuildMemberAdd` it
  fetches invites again and diffs the counters with `attributeInvite`. Joins are
  serialized per guild so two arrivals in one tick cannot both claim the same
  increment. Ties break on the invite code; an unchanged diff records the join
  with no inviter.
- **Persistence.** `invite_joins` with a unique
  `(guild_id, user_id, joined_at)` key, nullable `inviter_id`, JSONB
  `fake_reasons`, and `left_at` set on the newest open join. A duplicate gateway
  delivery is a no-op. Leaderboard totals are SQL aggregates, not process loads.
- **Advisory flags.** `account-age` (default 7 days) and `no-avatar`, stored on
  the join and optionally posted to one log channel. No punishment path exists in
  the port.
- **Surface.** `/invites` with `leaderboard`, `stats` and `who`, a 3-second
  per-user cooldown and guild-only guard. It is read-only.
- **Wiring.** `InvitePort` in the kernel, in-memory and Postgres adapters, a
  migration, runtime composition, gateway events and Discord log action.

## Why this feature, over the other P7 rows

The parity matrix had four unstarted domains: invites, forms/applications,
events/RSVP, and the community extras (modmail, auto-responders, role
persistence, analytics). Invites won on three counts:

1. **It is a complete, closed loop.** One join produces attribution, retention
   and flags; one command reads all of it. Forms and events need a modal/RSVP
   surface that the MCP cannot exercise at all.
2. **It proves a platform path Keystone had never used.** `GuildInvites` and the
   invite-counter diff are the join-side data anti-raid needs. No previous module
   had fetched or cached invites.
3. **Competitor research was decisive, and corrected the matrix.** MEE6 sells
   invite tracking as a separate paid plugin
   (https://wiki.mee6.xyz/en/plugins/invite-tracker). Dyno's module list
   (https://docs.dyno.gg/en/modules) and Carl-bot's logging and greeting docs
   (https://docs.carl.gg/logging.md, https://docs.carl.gg/greetings.md) contain
   no attribution, leaderboard or fake-invite detection. So this is paid parity
   plus a free differentiator, not a duplicate of three generalists.

Forms were the runner-up. They are more visible in a dashboard, but this pass
would have shipped a form builder, a submission store and a review UI without
being able to run a single real submission. Temporary ban/role expiry was also
considered: it depends on a scheduler path that is still unproven live, and a
half-verified expiry job is worse than a fully verified join tracker.

## What we tried and rejected

- **Storing a per-invite counter snapshot in Postgres.** It survives restarts,
  but adds a write per join and a second source of truth for a number Discord
  owns. The cache is process-local for now; the limitation is recorded rather
  than hidden.
- **Diffing only `uses`, ignoring the invite code.** Two invites changing in the
  same tick makes the result arbitrary. The code is the tie-breaker and the
  result is deterministic.
- **Punishing flagged joins inside the invite module.** Rejected: a first-time
  Discord user is indistinguishable from a throwaway by these heuristics.
  Moderation already has a dry-run-first policy; invites must not become a
  second, silent punishment path.
- **A settings subcommand.** The dashboard already edits every module schema
  through one write path. A second in-Discord editor would be a parallel
  configuration surface with no new capability.
- **A new `/invite` singular root.** Discord names must be unique across modules;
  `/invites` reads as the domain and leaves `/invite` available for a future
  single-use invite creator.

## Limits

- Live member join and live Postgres are unperformed.
- The cache is process-local; a restart between two joins can lose one
  attribution, and there is no backfill.
- The MCP cannot invoke slash commands; the live proof uses the dev `!` bridge.
- The leaderboard is embed-only, so the text-mode MCP cannot inspect it.

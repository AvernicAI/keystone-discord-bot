# Pass 05 — 2026-11-01 — P2 moderation & security

## What changed

- **One case spine.** `case_counters` (migration 0003) allocates a monotonic
  number per guild atomically; `DrizzleCaseStore` persists cases, events and
  state. `CaseService` owns opening cases, notes, review and appeal transitions.
- **Contract extension.** `InteractionLike` now carries parsed `options` and
  `channelId`; `ReplyInput` can carry action rows. `ModerationActions` and
  `CaseServicePort` are structural kernel capabilities, wired in the composition
  root. `ADR-0007` records why.
- **Security engine.** `SecurityEngine` turns joins, messages, webhooks and
  audit-log actions into findings. `SecurityCoordinator` writes the case before
  calling an action, appends the result and posts the case/appeal/verify card.
- **Commands.** `/mod` is one hub for ban, kick, timeout, warn, purge,
  lock/unlock, slowmode, case, note, history and review. `/appeal` is a target-
  owned transition; `/verify` clears quarantine. All use the normal registry
  and guards.
- **Discord seam.** `moderation-actions.ts` performs permission-prechecked
  actions; `moderation-events.ts` translates gateway events. `automod.ts` syncs
  only `Keystone ·`-prefixed native rules when explicitly enabled.
- **Tests and docs.** Added the scripted raid, dry-run, command, appeal,
  verification, native-plan and PGlite case-store suites, plus the module
  Spec/Status/Teaching docs. The 10 s test ceiling was raised to 30 s because
  several PGlite suites now run in parallel; no test was removed or skipped.

## What we tried and rejected

- **Discord API calls inside the module.** Tests would need a token and guild,
  and 403 handling would spread across commands. The action port keeps the seam
  in `apps/bot`.
- **Writing the case after the action.** A failed ban would leave no record.
  Cases are opened first and survive a failed external call.
- **A separate "alert-only" code path.** Dry-run is a setting in the one policy
  and one coordinator, so the test and production cannot diverge.
- **Native AutoMod as the whole scanner.** Discord cannot express our evidence,
  appeals or review queue; it is a second layer.
- **Treating PGlite as a live Postgres server.** The case-number and event tests
  are honest about using PGlite; a server run is still open.
- **Claiming a live gateway run.** No token or guild is available here. The
  Discord action adapter, gateway listeners, buttons and native sync typecheck
  but are not observed live.
- **Adding Components V2 now.** P2 uses one action row for appeal/verify; the
  40-slot budgeter remains P3 work.

## Verification

```
pnpm install --frozen-lockfile   exit 0
pnpm check                      exit 0 — typecheck, 70 tests / 13 files,
                                6/100 commands, memory checks pass
pnpm build                      exit 0 from a removed dist
pnpm test -- modules/moderation # 12 tests
pnpm test -- packages/db/src/cases.test.ts # 2 PGlite tests
```

The scripted raid test asserts: 10 joins, 5 invite posts and one webhook produce
20 cases; enforcing mode makes 11 quarantine, 5 delete-message, 1 delete-webhook
and 1 timeout calls; every case has a reason and an appeal button. The default
dry-run makes no punitive calls and leaves every resulting case `alerted`.

Still requiring a live service: Discord gateway events, real ban/kick/timeout/
purge/lock calls, button interactions, native AutoMod sync, and a Postgres
server. The join-gate expiry job and temporary-role/ban expiry are not wired yet;
the case model is ready for them.

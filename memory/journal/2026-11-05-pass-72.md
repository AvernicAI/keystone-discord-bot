# Pass 72 — portable case export

**Date:** 2026-11-05
**Phase:** P7.5
**Type:** product slice in the moderation module.

## Why

The case file was readable only as embeds. A moderator could see a case, but
could not hand one to a reviewer, a legal contact or a spreadsheet without
copying text by hand. `/export guild` carries cases inside a whole-server
bundle, which is the wrong shape for "send me case #412 and its history".

The competitive survey found no generalist documenting a complete case export.
That makes this the cheapest visible proof of the exit guarantee: the record a
server depends on can leave the bot intact.

## What changed

### An option, not a command

Discord caps a root at 25 subcommands and `/mod` already has 16; a 17th would
fit, but the feature is a second way to read rows the command already owns, not
a new action. `/mod case` and `/mod history` gained a `format` option:

```text
/mod case case:412 format:json
/mod history user:@member count:25 format:csv
```

Without `format`, both commands keep their existing embeds exactly. The
`history` range is capped at 50 and defaults to 10, matching the old list.

### One service, two renderings

`modules/moderation/src/case-export.ts` reads through a narrow
`Pick<CaseStore, "get" | "list" | "listEvents">`, so it accepts either the store
or `CaseService` and cannot write anything:

- **JSON** carries every case and its append-only events, plus the export time,
  counts and checksum. This is the format to hand to a reviewer.
- **CSV** is one row per case with the event count and a compact history cell.
  Cells containing a comma, quote or newline are quoted and doubled, so a
  multiline reason stays one row.
- **Checksum** is SHA-256 over canonical JSON of the normalized case/event
  payload. `exportedAt` is deliberately outside the hash, so the same content
  exported twice keeps the same digest, and the JSON and CSV of one case agree.

The command replies ephemerally with the attachment, the counts and the full
checksum. The file also carries it: a `checksum` field in JSON, a `checksum`
column in CSV.

### What it deliberately does not do

No new table, no stored export and no background job. The rows already in
`CaseStore` are the source. A missing case is a `UserError`, not an empty file.
The service never fetches a member, so an export does not leak a display name
the case did not already store.

## Verification

- New `case-export.test.ts` (4 tests): one case with two events and a valid
  64-character checksum; an unknown case returns `undefined`; CSV quotes a
  comma/quote/newline reason and matches the JSON checksum; a member-scoped
  range honours the limit and leaves out another member.
- `mod.test.ts` gains 3 command cases: `/mod case format:json` attaches
  `keystone-case-1.json` and opens no second case; `/mod history format:csv
  count:2 user:` attaches header + two newest rows for that member; no format
  still returns the embed with no attachment.
- `pnpm typecheck` clean. Focused: 39 tests across the new file, `mod.test.ts`
  and the command-localization contract.
- Full `pnpm test`: **644 tests in 94 files**. Budget stays **20/100 roots,
  141 subcommands, 161 actions** because the surface is two options.
- A real Discord file upload and download is adapter-tested through
  `ReplyInput.files`; the MCP cannot upload or fetch an attachment, so a live
  download is not claimed.

## What we tried and rejected

- **A `/mod export` subcommand.** It fits the 25 cap, but it is a second door
  to the same rows and spends the per-command budget for no new capability.
  An option on the read that already selects the rows is smaller.
- **Reusing `/export guild` with a case filter.** That path returns the whole
  server snapshot and requires `ManageGuild`; a moderator with only
  `ModerateMembers` could not use it, and the bundle is the wrong shape for one
  case.
- **Two files, one for cases and one for events.** It makes the checksum
  ambiguous and doubles the attachment surface. JSON nests events; CSV
  summarizes them in one escaped cell.
- **One CSV row per event.** Spreadsheet users expect one row per case, and a
  case with no events would need a synthetic row. The history cell keeps the
  event detail without breaking that shape.
- **Hashing the exact attachment bytes.** JSON needs its checksum inside the
  file, so it cannot hash itself. Hashing the normalized content gives one
  digest that survives formatting and agrees between JSON and CSV.
- **Storing the export for later download.** It adds a table and a retention
  question for data that is already durable in `cases` and `case_events`.
- **Including a member's current username.** The case stores ids, not a profile
  snapshot; resolving one at export time would make the file depend on gateway
  state and could expose a name the record never had.

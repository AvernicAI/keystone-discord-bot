# Pass 33 — Context menus: the right-click surface

**Date:** 2026-11-01
**Phase:** P7
**Tree before:** `5aad944` (clean) · 17 roots / 108 subcommands / 339 tests
**Tree after:** this pass · 17 roots / 108 subcommands / 4 context menus / 360 tests

## Why this was the gap

The approved v1.0 plan ended with four context menus, and no pass had built
one. The kernel could describe chat-input commands only: `CommandDefinition`
had no type, the registry keyed commands by name alone, `pnpm budget` counted
every registration against the 100 chat-input slots, and the bot ignored every
interaction that was not `isChatInputCommand()`. None of the four menus existed
in code or in Discord.

The four were named in the plan and are useful to different roles:

| Menu | Type | What it does | Reuses |
| --- | --- | --- | --- |
| **Report message** | message | Opens a moderation case with the message id and a bounded excerpt | `CaseService.open` |
| **Case history** | user | Shows the selected member's recent cases | `CaseService.list` |
| **Rank card** | user | Shows level, XP and server rank for the selected member | `LevelingService.rank` |
| **Explain with AI** | message | Asks the AI why a message may be a concern | `AiService.explain` |

## What changed

### Kernel: type-aware commands, separate budgets

- `CommandType` is `"chat-input" | "user" | "message"`. It defaults to
  chat-input everywhere, so every existing definition and fixture is unchanged.
- `InteractionLike` gained `commandType`, `targetId`, `targetUserId` and
  `targetContent`. The dispatcher resolves `registry.getCommand(name, type)`,
  which is why a user menu and a message menu may share a display name without
  colliding.
- `validateManifest` uses a separate `CONTEXT_MENU_NAME_PATTERN` that permits
  spaces and capitals (`"Explain with AI"`), and rejects options, subcommands or
  groups on a menu — Discord accepts none of them.
- `auditMeasurements` counts chat-input roots against 100 and user/message menus
  against their own 15 + 15 budgets. `formatBudgetReport` prints the menu list
  separately. The overall `status` still fails the gate on either limit.

### Adapter and registration

- `asInteractionLike` handles all three interaction kinds. Message menus expose
  the target author and content when Discord provides them; an absent
  `MessageContent` intent produces an empty string, and the commands say so
  honestly instead of inventing text.
- `buildApplicationCommandJson` chooses the slash or context-menu payload from
  the definition; `buildContextMenuJson` emits `type: 2` or `3` and no
  description. Boot sync and `pnpm commands:doctor` use the same function, so the
  two cannot disagree.
- `commandDrift` keys by `type:name` and normalises `type ?? 1`. Changing a
  menu's type is therefore reported as one missing and one extra registration,
  which is what Discord's per-type namespaces mean.
- `apps/bot/src/index.ts` now forwards user and message context-menu
  interactions to the same `dispatchCommand`.
- `/help` filters menus out of the typed catalog (they are not slash roots) and
  adds one sentence pointing at right-click → Apps.

### The four commands

- **Report message** requires a guild, has a 5-second cooldown, refuses a
  self-report, and stores `messageId`, `channelId` and an excerpt capped at 500
  characters as case evidence. It never deletes or punishes.
- **Case history** requires `ModerateMembers`, because case data identifies
  members, then reads the same `CaseService.list` rows as `/mod history`.
- **Rank card** reads the same `LevelingService.rank` projection as `/rank view`.
  The card is an embed, not a fake PNG: this build has no image renderer, and the
  footer says so.
- **Explain with AI** requires `ManageMessages`, calls the same
  `AiService.explain` path and `replyAnswer` as `/ai explain`, and therefore
  honours `ai.explanations`, the guild cap and the zero-retention policy. It
  replies with the advisory banner rather than an action claim.

### What the MCP could not do

The Discord MCP account posts and reads messages; it cannot right-click a
message or member and choose Apps. The four handlers were therefore **not
invoked live**, and this pass does not claim they were. Their paths are covered
by tests that use the real adapter shape:

- `apps/bot/src/adapt.test.ts` — `asInteractionLike` maps user and message
  targets; payloads are type 2/3 and carry no description.
- `packages/kernel/src/context-menus.test.ts` — registration, type-keyed
  lookup, separate budgets, rejection of options/subcommands and dispatch of a
  user menu.
- `modules/moderation/src/context.test.ts` — a report opens a real case whose
  evidence carries `messageId: "message-1"`, and case history reads the row.
- `modules/ai/src/context.test.ts` — explain uses the AI service, honours a
  disabled `explanations` switch and produces no case.
- `modules/community/src/context.test.ts` — rank card reads a seeded `4 / 400`
  level row and reports rank #1 without mutating XP.

## Cross-check: the rank card reports a real row

The community test seeds `InMemoryCommunityStore.setLevel("guild-a",
"author-1", 4, 400)` and then asserts the embed says `Level **4** · **400 XP**
· rank **#1**`; it reads the same store afterwards and finds the row unchanged.
The command constructs the same `LevelingService` as `/rank view`. There is no
second XP projection and no hard-coded number in the menu.

The moderation report test makes the equivalent check for a case: after
`reportMessage.execute`, `cases.list("guild-a", { targetId: "author-1" })`
returns exactly one `report` case with `evidence.messageId = "message-1"`.

## What we tried and rejected

- **A second "menus" registry.** Rejected. A context menu is an application
  command with a different type; a parallel registry would let `/help`, the
  budget and bot sync disagree. One registry, keyed by type.
- **Counting menus against the 100-root budget.** Rejected. Discord gives
  context menus their own 15 + 15 slots; counting them as roots would make the
  ledger wrong and could block a real root for the wrong reason.
- **Rendering a PNG rank card.** Rejected for this pass. `canvas`/`sharp` is a
  native dependency with no install proof here, and shipping an image-shaped
  placeholder would be the plausible-fiction failure the earlier passes were
  told to avoid. The embed is honest and the footer says it is a projection.
- **Letting Report message delete the message.** Rejected. A context menu is
  easy to misclick; the menu opens a reviewable case, and a moderator keeps the
  decision.
- **Skipping `ModerateMembers` on Case history because it is "just a read".**
  Rejected. Case rows contain targets, reasons and moderator ids; a read is a
  disclosure.
- **Sending a menu description to Discord.** Rejected. Discord's context-menu
  payload has no description field; the description remains registry/docs
  metadata.

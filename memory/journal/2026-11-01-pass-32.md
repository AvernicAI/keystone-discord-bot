# Pass 32 — `/music`: a real queue and a refusal you can trust

**Date:** 2026-11-01
**Phase:** P7 (last named v1.0 root; music itself is P8)
**Commit:** pending at the time of writing
**Previous pass:** [pass 31](2026-11-01-pass-31.md)

## Why this root

`/music` was the last unbuilt root in the approved v1.0 plan. It is also the
one root that cannot be honest by default: every competitor that once shipped
music removed it (MEE6 in 2023) or never had it, and the easiest demo is a
queue view that reports tracks nobody can hear.

So the pass splits the capability at the seam:

- **Saved queue** — real rows, a cap, remove/clear, durable in SQL mode. Shipped.
- **Playback** — a `MusicPlayback` port with one adapter. This build has no
  Discord voice client, no Lavalink client and no `LAVALINK_URL`, so the adapter
  refuses and names exactly what is missing. Not shipped.

That is the whole design decision. A queue that is real is useful for planning
and for a future player; a fake "now playing" line is worse than no command.

## What changed

`/music` is one new root in the new **music** module:

| Subcommand | What it does | Status |
| --- | --- | --- |
| `status` | Module state, queue count, playback availability and the exact blocker. Works while disabled. | Real |
| `queue` | Lists the saved queue (first ten). | Real |
| `add` | Validates an http(s) URL, derives a label, appends a track. | Real |
| `remove` | Removes one track by 1-based position; `ManageGuild`. | Real |
| `clear` | Clears the queue; `ManageGuild`. | Real |
| `play` | Calls the playback port. | Refuses (no backend) |
| `skip` | Calls the playback port. | Refuses (no backend) |
| `stop` | Calls the playback port. | Refuses (no backend) |

One root and eight subcommands. Discord reports **17 roots / 108 subcommands /
125 actions**; the budget gate is 17/100 roots.

### The shape

- `packages/kernel/src/music.ts` defines `MusicTrack`, `MusicQueue`,
  `MusicStore`, `MusicPlayback`, `MusicPort` and the stable
  `community_records` identity (`music_queue` / `default`). Nothing imports
  discord.js or Drizzle.
- `modules/music/src/music.ts` owns policy: settings through the module schema,
  URL validation, the disabled rule and propagation of a playback refusal into
  a `UserError`.
- `modules/music/src/store.ts` is the in-memory queue; mutations are serialized
  per guild and the cap is enforced inside the store.
- `packages/db/src/music-store.ts` is the SQL queue over the existing
  `community_records` table. Every mutation runs in a transaction and takes
  `SELECT ... FOR UPDATE` on the guild row, so concurrent adds cannot both take
  the last slot. No migration was needed.
- `modules/music/src/playback.ts` is the one unavailable adapter. It returns
  `available: false`, `backend: "none"` and the missing list.
- `modules/music/src/commands/music.ts` is guards and rendering. Guild-only,
  two-second cooldown; `remove` and `clear` add `ManageGuild`.

Settings are `enabled` (default **false**) and `maxTracks` (1–100, default 25).
The manifest requests only `Guilds`; a build that cannot join voice does not ask
for `GuildVoiceStates`.

### The SQL cross-check

The live window has no Postgres, so the queue's persistence is proven on PGlite
instead of claimed live. `packages/db/src/music-store.test.ts` writes two tracks,
then reads the raw table rather than calling the adapter's own `list()`:

```text
select guild_id, kind, key, data from community_records where guild_id = 'guild-a'
→ one row: guild_id 'guild-a', kind 'music_queue', key 'default',
  data.tracks length 2
```

It also proves remove and clear delete the row, five concurrent adds against a
cap of three add exactly three, and guild B's rows never appear in guild A's
queue.

## What we tried and rejected

- **A fake "now playing" reply.** It is the easiest way to demo `/music` and the
  clearest lie in the repo. `play` calls the port, and the port says it cannot
  play.
- **Adding a voice or Lavalink dependency.** The pass was not authorized to add
  an external dependency or service, and `GuildVoiceStates` without a client is
  a permission prompt with no behaviour behind it.
- **A `music_queue` table.** `community_records` already has the right identity
  `(guild, kind, key)` and a testable unique key. A new table would be a second
  place to migrate and reconcile.
- **Storing `nowPlaying`, `currentIndex` or `duration`.** Those belong to a
  player; the database cannot know them. A saved track is a URL and a label.
- **Enabling music by default.** A queue that appears configured before an
  operator opts in is the same advertising failure as an empty root. Default is
  false; `status` still explains how to enable it.
- **Enforcing the cap only in the command.** Two concurrent interactions would
  both pass the check. The store owns the cap and the lock; the command only
  renders the refusal.
- **Rendering the in-memory queue as a `community_records` row.** The status
  line is mode-neutral: it names the logical record and says the table applies
  in SQL mode. The first live draft claimed `community_records` in memory mode;
  that was corrected before the committed transcript.
- **Buttons in this pass.** Components are a UI-pass concern and would be a
  second state surface; the text commands are testable now.

## Limits

- **No audio plays.** There is no voice client, no Lavalink client and no
  configured node. The refusal is live-proven; streaming is open and the
  feature matrix says so.
- The live window is memory mode. The SQL queue is PGlite-proven, not
  live-Postgres-proven.
- The MCP cannot invoke slash commands, so the proof is the `!` bridge through
  the real registry, guards and reply adapter. A human `InteractionCreate` is
  still unobserved.
- `clear` and the button/embed surface were not read back live; they are covered
  by tests.
- `/music queue` shows ten tracks and truncates the rest by count.

# Pass 25 — auto-responders and the profanity delete proof

**Date:** 2026-11-01
**Phase:** P7 parity completion
**Commit:** pending (working tree)

## The choice

After the content filters, the highest-value open row in a different domain was
`parity-extra.auto-responder` (community). Dyno and Carl-bot both document
keyword replies; MEE6 keeps its equivalent behind a paid bundle. It is also the
rare missing feature that can be driven through the real gateway with one bot
account: the Discord MCP cannot invoke a slash command, but it can post a
message, and the existing `keystone-test:` marker makes that message visible to
a bot-friendly adapter.

The alternatives were weaker for this pass:

- **Forms or events** need modals/buttons and a second interactive client; they
  are a larger surface and harder to prove from MCP.
- **Modmail** needs a second human account to send a DM.
- **Panic mode** is a destructive guild-wide action, not an unattended test.
- **Message analytics** is useful but a read-only counter; the auto-responder
  has a visible user-facing reply and exercises the event path.

The pass also closed one cheap adjacent gap: profanity `delete` mode had only
been exercised in `alert` mode. The same live process could prove it with a
temporary seed, then restore the safe committed seed.

## What changed

### One service, one record seam

`modules/community/src/responder.ts` adds `AutoResponderService`:

| Concern | Behaviour |
| --- | --- |
| Storage | Guild-scoped `community_records` kind `responder`; no new table or migration |
| Match modes | `exact`, `contains`, `regex` (case-insensitive) |
| Precedence | Exact > contains > regex, then trigger text; never storage order |
| Limit | At most one reply per message |
| Cooldown | Per trigger, default `responders.cooldownSeconds` (10), overridable per trigger |
| Validation | Trigger length 1–100, response ≤1,500, valid regex, duplicate trigger/mode refused, guild cap |
| Mentions | Replies send with `allowedMentions: { parse: [] }`; a trigger cannot ping a role or `@everyone` |
| Write timing | `lastAt` is written only after a successful send, so a failed send retries |

`settings.ts` gains:

```ts
responders: {
  enabled: false,        // master switch
  max: 25,               // guild cap
  cooldownSeconds: 10,   // default per-trigger window
}
```

### Admin surface under `/tools`

No new root. `/tools` gains three actions:

- `responder` — `name` is the trigger, `value` the reply, `match` chooses
  exact/contains/regex and `limit` optionally sets the cooldown in seconds.
- `responders` — lists ids, modes, triggers and replies; `value=on|off`
  toggles the master switch.
- `responder-remove` — removes by the full id shown by `responders`.

The existing `ManageGuild` guard covers all three. `responders` shows the newest
10 with 40-character trigger/reply previews and the full id, keeping the reply
inside Discord's 2,000-character message cap even at the 25-trigger guild limit.

### The development marker has one owner

`apps/bot/src/dev-fixture.ts` now owns `BOT_TEST_MARKER` and
`botFixtureContent`. Moderation still re-exports the marker for its tests.
`community-events.ts` takes the same `{ botTestGuildId }` option as moderation.
A marker message from a bot:

1. is stripped and passed to `AutoResponderService` only;
2. never awards XP, touches the starboard or appends a ticket transcript;
3. is still refused outside `DEV_GUILD_ID` and in production (no option).

`runtime.ts` seeds the in-memory dev guild with `responders.enabled: true` and a
`hello keystone` trigger whose cooldown is 60 seconds. The trigger has no
production equivalent; the default remains off with an empty trigger set.

## Live evidence

The bot booted in memory mode as `AI Team#5758` with 11 commands current and
both `DEV_GUILD_ID` warnings. The first run used the 10-second seed and proved
the basic reply. The process was restarted with the final 60-second seed so the
cooldown check did not depend on tool latency.

### 1. A marker message fires the responder

```text
MCP 08:23:19.802  keystone-test: hello keystone
AI Team 08:23:19.992  Hi from Keystone's auto-responder.
```

The message was posted by the MCP bot (`AllTheMons GPT`), so this also proves
the marker path works for a bot author and that the responder, not the security
engine, is the only module that replies.

### 2. The cooldown suppresses the next reply

After the restart, the trigger fired again at 08:24:56:

```text
MCP 08:24:56.403  keystone-test: hello keystone
AI Team 08:24:56.568  Hi from Keystone's auto-responder.
```

A second identical message arrived 5.7 seconds later:

```text
MCP 08:25:02.141  keystone-test: hello keystone
```

No reply followed. `read_messages` showed the trigger message with no AI Team
message after it.

### 3. The cooldown releases

After the 60-second window:

```text
MCP 08:26:33.436  keystone-test: hello keystone
AI Team 08:26:34.169  Hi from Keystone's auto-responder.
```

This is the full cooldown contract on the real gateway: first reply, suppressed
second reply, released third reply.

After the final mention-policy change, one more boot of the committed code
proved the path still works end to end:

```text
MCP 08:49:37.142  keystone-test: hello keystone
AI Team 08:49:37.350  Hi from Keystone's auto-responder.
```

### 4. Profanity delete mode, with the safe seed restored afterwards

For this check only, the dev seed was temporarily:

```ts
dryRun: false,
automod: {
  links: "alert",
  linkBlocklist: ["phish.test"],
  profanity: "delete",
  bannedWords: ["pineapple"],
  zalgo: "alert",
}
```

The MCP posted `keystone-test: I really like pineapple pizza` shortly after the
08:27:25 ready log.
`read_messages` did not contain the message afterwards. `!mod filters` at
08:28:07 returned:

```text

```

The message was deleted and the case survived. The temporary seed was reverted
to `profanity: "alert"` with no `dryRun` override before this commit.

## What we tried and rejected

- **A new `auto_responders` table.** Rejected: `community_records` already gives
  guild-scoped `(kind, key)`, in-memory parity and a tested Postgres path. A new
  table would add a migration and a second access pattern for no capability.
- **All matching triggers reply.** Rejected: a phrase can match an exact, a
  contains and a regex trigger, and a wall of replies is worse than one. One
  reply, deterministic precedence.
- **Storage-order precedence.** Rejected: `listRecords` orders by `updatedAt`;
  editing a trigger would change which reply wins. Sort by match mode, then
  trigger text.
- **A guild-wide cooldown.** Rejected: a noisy trigger would silence every other
  trigger. Cooldowns are per trigger, with an optional override.
- **Compiling every regex on every message.** Rejected for validation *and*
  matching: validation compiles once at save; matching compiles only the regex
  candidates that reach the runner. The trigger is capped at 100 characters.
- **A new `/responder` root.** Rejected: `/tools` is the utility hub and the
  budget stays at 11/100.
- **Writing the cooldown before the send.** Rejected: a Discord failure would
  burn the window. `lastAt` is written after `sendMessage` returns ok.
- **Driving the event path through `!tools` only.** Rejected: the prefix bridge
  invokes commands, not message events. The dev marker is the existing
  message-event seam; reusing it keeps one fixture story.

## Limits

- The admin actions were not run live because the MCP bot does not hold
  `ManageGuild`; they are covered by command tests. The trigger and cooldown path
  ran live with a seeded record.
- Regex is operator-owned and compiled as-is. There is no ReDoS sandbox or
  safe-pattern linter beyond the 100-character cap; the feature is admin-only and
  default-off.
- The live author was the MCP bot, not a human member. The ordinary-member test
  covers the same adapter branch, but a human author is still staging work.
- The dev seed is process-local. The Postgres record path is proven on PGlite,
  not a live Postgres server.
- The profanity delete proof is live; the zalgo delete branch still needs a
  disposable fixture.

# Pass 39 — The join gate owns its own DM

**Date:** 2026-11-01
**Phase:** P7
**Tree before:** `edaccde` (clean) · 17 roots / 117 subcommands / 134 actions / 4 context menus / 398 tests
**Tree after:** this pass · same ledger and counts · 398 tests / 59 files

## The finding

`/verify start` sent its DM with `ctx.community.actions.sendDM`. The moderation
module only compiled because `CommandContext` exposes the community port to
every module; `modules/moderation/package.json` has no dependency on
`@keystone/module-community`. If the composition root ever stopped wiring the
community adapter, the join gate would fail with a message about a port it
never declared. A verification flow should not borrow another module's
adapter.

## What changed

The DM is now a member of the moderation port the module already owns:

- `packages/kernel/src/types.ts` — `ModerationDirectMessage` (content plus
  optional components) and
  `ModerationActions.directMessage(userId, message)`. The result reuses
  `ModerationActionResult`, so `ok: false` carries the provider detail.
- `apps/bot/src/moderation-actions.ts` — the Discord implementation fetches the
  user and sends the content/buttons. A closed DM or missing user becomes
  `{ ok: false, detail }`, exactly as the community adapter did.
- `modules/moderation/src/commands/verify.ts` — `start` calls
  `moderation.actions.directMessage`. The `ctx.community` check and its
  "DM verification path is not configured" branch are gone; the
  `moderationPort` helper now guards the only dependency the command has. The
  DM body, the verify button, the success reply and the
  `I could not DM you (…). Open DMs from server members…` refusal are unchanged.
- `modules/moderation/src/mod.test.ts` — `RecordingActions` records
  `directMessage` calls and can return a failure detail. A small
  `verificationStart` helper builds the command context with **no community
  port at all**, so the test itself proves the dependency is gone.
- The other `ModerationActions` fakes
  (`modules/moderation/src/security.test.ts`,
  `apps/bot/src/interaction-harness.test.ts`,
  `apps/bot/src/moderation-buttons.test.ts`) implement the new method.
- `CommunityActions.sendDM` stays: reminders and giveaway winners still use it.
  No other module lost a capability.

## Behavior and cost

Preserved: the DM content, the `keystone:verify:<guildId>:<userId>` button, the
`ephemeral: true` guild reply after a successful send, the closed-DM refusal
text, the no-record/gate/verified refusals, and the command surface. One branch
necessarily disappears: with moderation wired but community absent, the old
command refused because it needed the community adapter. That refusal was the
bug; the command now succeeds because moderation delivers its own DM. With
moderation absent, the existing "Verification state is not configured…" error
still fires before anything else.

The cost is one kernel type, one method on an existing port, about a dozen
lines in the Discord adapter, and four test fakes. No new file, port, module,
table, migration or package dependency; no command or menu was added.

## Tests

The two DM paths now run through the moderation port:

- **success** — a quarantined member gets exactly one `directMessage` for the
  right user, with the `Keystone verification` content and the guild-scoped
  button id; `start` still leaves the row quarantined and unverified.
- **failure** — the port returns `{ ok: false, detail: "Cannot send messages to
  this user" }`; the command throws the same "could not DM you" refusal and the
  port was called once.
- The no-record, disabled-gate and already-verified tests still assert that
  `directMessage` is never called.

The focused suite (moderation module, button adapter, synthetic slash harness)
is 61 tests across 6 files; the full gate is below.

## What we tried and rejected

- **A new `VerificationNotifier` port.** Rejected: it adds a fifth moderation
  seam for one method. `ModerationActions` already is the module's Discord
  surface, and a DM is an action.
- **Move `sendDM` off `CommunityActions`.** Rejected: reminders, giveaways and
  other community flows use it. Removing it to punish the dependency would break
  live features.
- **Import the community adapter in `apps/bot` from moderation.** Rejected: that
  is the same coupling at a different layer and would make moderation's tests
  pull in community.
- **Reuse `CommunityMessage` for the port.** Rejected: it carries embeds,
  ephemeral flags and mention policy that a verification DM does not need. A
  narrow type is the honest contract.
- **Add a quarantine command or dev seed to prove the DM live.** Rejected:
  seeding the MCP account as quarantined would fake a member lifecycle and add
  command surface just for a transcript. The MCP cannot receive the DM anyway.
- **Change the success copy while touching the path.** Rejected: a
  behavior-preserving move must not edit what members read.

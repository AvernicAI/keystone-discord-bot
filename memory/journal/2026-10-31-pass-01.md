## What we tried and rejected

- **`Sapphire` framework.** It already has stores, pieces and preconditions, so it was the "don't build it" option. Rejected because we would inherit its release cadence, its types would leak into every module, and its 2026 maintenance signal could not be verified. We copied the *ideas* (store, piece, precondition) instead of the dependency. Recorded in ADR-0005.
- **`oceanic` instead of discord.js.** Smaller, modern, plausible. Rejected: no living all-in-one flagship uses it, and contributor familiarity matters more than a benchmark nobody has published. ADR-0001.
- **Turborepo on day one.** It buys caching we do not need for two packages, and every contributor would pay the config tax. Deferred to P1 with a real build graph; `pnpm -r` is enough today. Revisit when `apps/web` lands.
- **Per-package `tsconfig` files.** Twelve near-identical configs are a merge-conflict farm. One root project plus pnpm-linked source packages keeps the editor honest and the diff small.
- **Loading commands with a filesystem glob.** Windows path handling and bundler differences make glob loaders flaky. An explicit `modules` array in one file is boring, obvious, and impossible to get subtly wrong. Revisit at ~30 modules if the list hurts.
- **Putting TypeScript build output in the repo.** Dev-first source resolution (`exports` → `.ts`) means no build step in the contributor loop. ADR-0002 records the P1 build-plan requirement.
- **A JSON config file for guild settings.** Rejected outright: per-guild config belongs in the database behind a Zod schema. This is the anti-pattern that makes self-hosted bots unmaintainable.
- **Bundling a YouTube music source.** Not a technical question. Groovy and Rythm were killed by cease-and-desist, and MEE6 removed music in 2023. Music stays opt-in, bring-your-own Lavalink (Q-3).
- **MIT license, chosen by default.** Deliberately left open. Choosing a license is the user's call, and the repo should not quietly make it for them. Q-1.
- **`pnpm approve-builds` interactively.** It works, but it writes machine-local state and asks a question; a fresh clone or CI would still fail. The allow-list belongs in the repo, not in one developer's config.
- **`pnpm.onlyBuiltDependencies` in the root `package.json`.** pnpm 12 no longer reads the `pnpm` field at all — it warned and ignored it. The setting now lives in `pnpm-workspace.yaml`.
- **`onlyBuiltDependencies` in `pnpm-workspace.yaml`.** Still accepted by `pnpm config list`, but install kept failing with `ERR_PNPM_IGNORED_BUILDS`. pnpm 12 expects the `allowBuilds` map (`esbuild: true`), which is what `approve-builds` writes. Verified by a clean install.
- **Weakening the payload-cap test.** The original test could not reach 8,000 characters because manifest validation already enforces 25 options × 100-char descriptions. Rather than delete the check, the audit was split into a pure `auditMeasurements()` and the limit is now tested directly.

## Verification

Run on 2026-11-01, all green:

```
pnpm install       # exit 0; esbuild postinstall ran; lockfile up to date
pnpm typecheck     # exit 0; strict tsc, no emit
pnpm test          # exit 0; 4 files, 30 tests passed
pnpm budget        # exit 0; 2/100 commands, status OK
pnpm memory:check  # exit 0; 32/32 checks passed
```

Two test failures were found and fixed during this pass, both in the tests:
an intents test registered a module with zero commands (validation correctly
rejected it), and the payload test asserted a failure that valid Discord limits
cannot produce. One real type error was also fixed: `editReply` cannot take the
ephemeral flag, so the adapter now has a separate `toEditOptions` cast.

Boot path: `DISCORD_TOKEN= pnpm start` exits 1 with the intended "copy
.env.example" message and no token is read. `pnpm budget` registers every real
module manifest, so registration itself is exercised. Not verified: a live
gateway login (needs a token) and the CI workflow itself (no remote yet). Those
are reported as untested rather than assumed working.

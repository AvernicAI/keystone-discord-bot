## What changed

The pass-40 inventory found two plan roots that were never built: `/event` (7
subcommands) and `/modmail` (6). This pass ships `/event` only.

**Contract and tables**

- `packages/kernel/src/events.ts` — `EventDefinition`, `EventRsvp`,
  `EventStore`, typed create/RSVP results. `CommandContext` and `DispatchDeps`
  gained an optional `events` store.
- `packages/db/src/migrations/0012-events.ts` — `events` and `event_rsvps`.
  `(guild_id, key)` is unique; `(event_id, user_id)` is unique; the RSVP foreign
  key cascades.
- `packages/db/src/event-store.ts` — the Drizzle adapter. `upsertRsvp` locks the
  event row and counts `going` rows inside one transaction, so the last seat
  cannot be sold twice.

**Module**

- `modules/events/src/events.ts` — `EventService` owns date parsing, the
  draft/open/closed lifecycle, the event cap, the capacity bound, the
  delete-only-without-attendance rule and the reminder write.
- `modules/events/src/store.ts` — the in-memory store with the same rules.
- `modules/events/src/commands/event.ts` — `/event create | edit | delete |
  list | rsvp | remind | export`. Management branches check `ManageGuild`;
  `list` and `rsvp` stay member-facing.
- Registered in `packages/module-catalog`, composed in `apps/bot/src/runtime.ts`
  and `apps/bot/src/index.ts`.

**Two debts from the inventory**

- `modules/forms/src/store.ts` — removed `allSubmissions`, which no code called.
- `memory/vault/01-Mission/Master-Plan.md` — replaced the "no per-root list"
  note with the durable table: 14 rows with a planned count (13 built roots plus
  the unbuilt `/modmail`), **72 planned names**, and the **132 registered** count
  per root. Six registered roots are not in the plan table. The 160 figure still
  has 28 unnamed slots and no 18th root, so it is not a target.

**Behaviour, exactly**

1. `create` writes a `draft`; `edit` moves between draft, open and closed.
2. `rsvp` is refused outside `open`. It writes the invoking member's row only;
   there is no `user` option. A second answer updates that row.
3. Capacity counts `going` only. A decline frees a seat. A full event refuses
   `going` by name and still accepts `not_going`.
4. `remind` requires `open`, records `reminded_at`/`reminded_by`/`reminder_count`
   and then posts the reminder.
5. `delete` requires `confirm` and refuses while any RSVP exists.
6. `export` attaches `keystone.events` JSON with counts and a SHA-256 checksum.

## What we tried and rejected

- **Store events in `community_records`.** Rejected: an RSVP needs a stable
  foreign key, a unique membership and an atomic capacity count; a JSON blob
  gives none of those.
- **Cache `going` in a counter column.** Rejected: two concurrent RSVPs would
  both read the old count and oversell. Count rows inside the transaction.
- **Delete the RSVP row on `not_going`.** Rejected: it loses the answer and
  makes attendance history lie. Keep the row and count `going`.
- **Let `rsvp` take a `user` option for staff.** Rejected: it breaks the
  ownership rule and gives moderators a silent way to attend someone else.
- **Ship RSVP buttons.** Rejected this pass: there is no component interaction
  layer, and a button that cannot be clicked is the dead end pass 33 avoided.
- **Schedule reminders with the existing queue.** Rejected as scope: it needs a
  recurring job, a per-event wake-up and a delivery port. Manual `remind` is
  real and recorded; the scheduler is named as open.
- **Emit ICS instead of JSON.** Rejected: ICS needs a calendar library or a
  careful serializer, and JSON is the format the other modules already export.
- **Start `/modmail` in the same pass.** Rejected: one vertical slice per pass,
  and modmail needs thread relay and DM delivery that the bot account cannot
  prove live.

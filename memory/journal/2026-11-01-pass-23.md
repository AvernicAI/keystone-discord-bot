# Pass 23 — link / phishing filter

**Date:** 2026-11-01
**Phase:** P7 parity completion
**Commit:** pending (working tree)

## The choice

`memory/machine/features.json` still listed `automod.link-phishing-filter` as
open. Dyno, Carl-bot and Wick all document a link filter; the parity matrix's
note was already `Local list + review queue`. It was the strongest remaining
security gap that can be exercised from this machine as a real Discord message,
so it won over the other open P7 rows (forms, events, modmail) which need a
second account, a browser, or a scheduler to prove end to end.

The implementation stays inside the existing module contract: two settings keys,
one new action under the existing `/mod` root, no new command, no new module and
no new dependency. The budget remains **11/100**.

## What changed

### Settings

`modules/moderation/src/settings.ts`

| Key | Default | Meaning |
| --- | --- | --- |
| `automod.links` | `off` | `off`, `alert` or `delete` |
| `automod.linkBlocklist` | `[]` | Up to 200 hosts; a blocklisted host also covers its subdomains |

Both keys live in the existing `automod` object, so the dashboard's existing
schema-validated write path can edit them without a web-only schema.

### Engine

`modules/moderation/src/security.ts`

`suspiciousLink(content, blocklist)` extracts `http(s)` URLs, normalises the
host (lowercase, `www.` and a trailing dot removed) and returns the first
suspicious one:

- a host equal to a blocklist entry, or ending in `.` plus that entry, is a
  **blocklist** match;
- a host with any `xn--` label is a **punycode** match even without an entry,
  because it can hide a lookalike domain;
- an ordinary link is left to Discord and native AutoMod.

The finding is `automod.link`, with `evidence: { host, match }`. In `alert`
mode it is an alert; in `delete` mode it is the existing `delete-message`
finding, so the coordinator, case, appeal button and notification path are the
ones already used by the invite filter. Only the host and the match kind are
stored; the full message is not archived.

### Command

`modules/moderation/src/commands/mod.ts`

`/mod links` (also `!mod links` in the dev guild) lists the newest link-filter
findings from the last 25 cases, including the case number, state, target and
reason. It is read-only. Review is the existing `/mod review case=N` path, so a
moderator closes the loop without a second queue or a new command root.

### Development seam

The Discord MCP posts as a bot, and the security adapter correctly ignores bot
authors. To prove the new rule without a second human account, a bot message in
`DEV_GUILD_ID` is evaluated only when it starts with `keystone-test:`. The
marker is stripped before evaluation; the event then follows the same
`SecurityCoordinator` path as a member message. `apps/bot/src/runtime.ts` seeds
the in-memory dev guild with `links: "alert"` and a local `phish.test` example so
the harness has a deterministic fixture. Neither behaviour exists in production:
the seed is guarded by `NODE_ENV !== "production"`, `DEV_GUILD_ID` and the
in-memory database mode, and the adapter receives no test guild there.

## What we tried and rejected

- **A remote threat-intelligence feed.** Rejected: it adds a network dependency,
  a privacy question and potentially a paid service. The blocklist is local,
  operator-owned data in the existing settings row.
- **A new `/links` root.** Rejected: `/mod links` is an action under an existing
  root, so it costs zero additional global commands and sits with the review
  queue a moderator already uses.
- **Always deleting punycode.** Rejected: `alert` and `delete` are separate
  modes; a punycode host is suspicious, but the operator decides the response.
- **Treating a blocklist entry as a substring.** Rejected: `phish.test` must not
  match `notphish.test`. Matching is equality or a `.`-suffixed subdomain.
- **Storing the whole message as evidence.** Rejected: the existing evidence
  policy keeps the trigger slice. The host and match kind are enough to review.
- **A test-only settings command.** Rejected: a product command used only by the
  harness is a second configuration path. The existing dev seed and a
  marker-prefixed message are smaller and clearly scoped.
- **Allowing every bot message in the dev guild.** Rejected: the bot's own
  replies would be scanned and could be deleted. Only the explicit marker is
  allowed, and it is stripped.

## Limits

- The live run used **alert** mode. The `delete` branch shares the coordinator
  and action path already exercised by the invite filter, but a live deletion
  from a link finding was not performed.
- The blocklist is host-only: no paths, wildcards, regex, remote reputation or
  allow-list yet. A bare domain without `http(s)://` is not parsed.
- Punycode detection is a heuristic; a legitimate internationalised domain will
  also be flagged until an operator allow-list exists.
- `/mod links` scans the newest 25 cases, not all history; it is a review aid,
  not an export.
- The marker seam is test scaffolding. It is never registered in production and
  does not change the slash-command surface.

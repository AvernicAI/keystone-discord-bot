**Date:** 2026-11-01
**Phase:** P7
**Tree before:** `59a303d` (clean) · 17 roots / 117 subcommands / 134 actions / 4 context menus / 398 tests / 59 files
**Tree after:** this pass · 18 roots / 125 subcommands / 143 actions / 4 context menus / 413 tests / 61 files

## What changed

The approved v1.0 plan's remaining P7 domain, forms/applications, is a real
vertical slice rather than a panel that prints instructions.

**Contract and tables**

- `packages/kernel/src/forms.ts` — `FormDefinition`, `FormFieldDefinition`,
  `FormSubmission`, `FormStore`, and typed create/submit results. `CommandContext`
  and `DispatchDeps` gained an optional `forms` store, the same shape as
  `analytics` and `music`.
- `packages/db/src/migrations/0011-forms.ts` — `forms` and `form_submissions`.
  `(guild_id, key)` is unique; `(form_id, user_id) WHERE state = 'submitted'` is
  a partial unique index. The second index is the real "one pending application"
  rule; the service pre-check only chooses the nicer message.
- `packages/db/src/form-store.ts` — the Drizzle adapter. `createForm` returns a
  typed `duplicate-key` result; `createSubmission` uses `ON CONFLICT DO NOTHING`
  and reads the existing pending row back; `reviewSubmission` updates only a
  `submitted` row.

**Module**

- `modules/forms/src/forms.ts` — `parseFieldSpec`, `parseAnswers` and
  `FormService`. Field keys are stable and explicit; every field is required;
  unknown keys, missing answers and oversized values are rejected before a write.
  The service owns the caps, the enabled switch, the open gate, the delete rule
  and the review transition.
- `modules/forms/src/store.ts` — the in-memory store with the same rules.
- `modules/forms/src/commands/form.ts` — `/form create | edit | delete | list |
  panel | submit | review | export`. Seven management branches check
  `ManageGuild`/`Administrator` inside the branch because the root guard cannot
  vary by subcommand; `submit` stays open to members.
- `modules/forms/src/settings.ts` — `enabled`, `maxForms`, `maxFields`,
  `maxSubmissionsPerForm`, `maxAnswerLength`.
- Registered in `packages/module-catalog`, composed in `apps/bot/src/runtime.ts`
  and `apps/bot/src/index.ts`. No new gateway event, no new intent, no new
  dependency, no new root beyond `/form`.

**Behaviour, exactly**

1. `create` writes a `draft`. `edit` can open or close it; `panel` refuses a
   draft and records the channel only after the panel message is posted.
2. `submit` validates every field, refuses a closed form, enforces the
   per-form cap, and writes one pending row. A second pending submission is
   refused by name with the existing id.
3. `review` with no `submission` lists pending rows; with a submission it shows
   the answers; with `decision` it transitions only a `submitted` row. A second
   reviewer gets "already accepted/denied" and nothing is written.
4. `delete` requires `confirm` equal to the key and refuses while any submission
   exists, pointing at `state:closed`. History is never erased by the command.
5. `export` attaches `keystone.forms.<guild>.json`, counts and a SHA-256
   checksum over the payload.

**Deferred, and named in the surface**

- **Modal input is not in this build.** There is no modal method on
  `InteractionLike`, no modal-submit adapter and no UI layer. `submit` takes a
  validated `answers` option and the panel prints the exact syntax. No button was
  added that opens nothing.
- `/export guild` does not include forms or submissions. `PortabilityService`
  does not know the tables; `/form export` is the truthful dedicated export. The
  gap is open in Status and Next.
- No review-channel notification. That would need a narrow forms delivery port;
  borrowing `community.actions` is the coupling pass 39 removed from moderation.

## What we tried and rejected

- **Store forms and submissions in `community_records`.** Rejected: the generic
  record table is owned by the community module, so forms would either borrow
  that store or duplicate it, and a JSON blob cannot enforce one pending
  submission per member. Two tables are justified by a real transition and a
  real invariant.
- **One table with `kind = 'form' | 'submission'`.** Rejected: the foreign key
  from a submission to a form, the partial unique index and the not-null answer
  column all become conditional.
- **Make `/form submit` open a modal.** Rejected this pass: it requires a kernel
  method, a second interaction type in the adapter, dispatch support and a
  renderer. Shipping the validated answer option is smaller and honest; the
  modal layer can call the same `FormService.submit`.
- **Post the panel through `ctx.community.actions.sendMessage`.** Rejected: it
  repeats the exact dependency smell pass 39 fixed for moderation. The panel is
  posted in the invoking channel with the normal reply adapter and records that
  channel; no cross-channel send is needed yet.
- **Delete a form and cascade its submissions after a confirmation.** Rejected:
  a review queue exists to preserve a decision trail. `delete` is for unused
  drafts; `closed` is the archive state.
- **Reuse the settings array for form fields.** Rejected: a settings write would
  silently change the meaning of answers already stored, and submissions need a
  stable `form_id`.
- **Echo the answers in the submit reply.** Rejected: slash replies are
  ephemeral, but the development bridge posts ordinary channel messages. The
  reply names the submission id and the answer count only.
- **Add a management-only root guard.** Rejected: `submit` must be member-facing.
  Branch-level permission checks keep one root and an accurate refusal.
- **Extend the portability bundle in this pass.** Rejected as scope: it touches
  `GuildSnapshot`, restore ordering and the PGlite round-trip. The omission is
  stated rather than hidden.

## Cost

- **One new kernel port** (`FormStore`) and the value types it carries.
- **Two tables and one migration** (`0011-forms`): `forms`, `form_submissions`.
- **One new module** (`modules/forms`, 6 source files): manifest, settings,
  service, in-memory store, command hub, index.
- **Two new SQL-side files**: the Drizzle adapter and its PGlite test.
- **No new root beyond `/form`.** One global slot, eight subcommands, five
  options on `create` and 143 total actions in the ledger.
- **No new dependency, no new intent, no new paid service.** `pnpm-lock.yaml`
  changed only because the new workspace package was linked.

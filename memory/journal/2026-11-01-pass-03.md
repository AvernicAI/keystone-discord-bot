# Pass 03 — 2026-11-01 — P1 substrate

## What changed

- **`packages/db`.** Drizzle schema for the whole P1 spine: `guilds`, `settings`
  (unique per guild+module+key), `members`, `cases` + `case_events`, `tickets`,
  `levels` / `xp_events`, `economy_ledger`, `audit_events`, `job_receipts`,
  `imports`, `backups`. Two ordered migrations, a transactional migrator with a
  `schema_migrations` ledger, `DrizzleSettingsRepository`,
  `PostgresIdempotencyStore`, and `probeDatabase`.
- **`packages/cache`.** `RedisCooldownStore` using a single `SET key 1 PX ttl NX`
  (one atomic operation), with an explicit and logged in-memory fallback only
  when `REDIS_URL` is unset.
- **`packages/queue`.** `BullJobQueue`, `createBullWorker`, W3C traceparent in job
  data, idempotency before/after the handler, terminal failure recording, and an
  `InProcessJobQueue` driver with the same retry contract for environments with
  no Redis.
- **`packages/telemetry`.** A four-method `Telemetry` port implementation over
  OpenTelemetry; off with no provider when unconfigured; OTLP exporter loaded
  only when an endpoint is set; async context manager installed once so
  `traceparent()` is real.
- **Kernel.** New ports (`CooldownStore`, `JobQueue`, `IdempotencyStore`,
  `HealthProbe`, `Telemetry`); the cooldown guard now calls the store; dispatch
  opens one command span and injects the ports.
- **`modules/setup`.** `/setup` registered through the normal registry, behind
  `ManageGuild`, reporting database/migrations/cache/module readiness without
  writing anything.
- **`apps/worker`.** BullMQ consumer with a real `settings.snapshot` handler that
  writes an audit record, plus graceful shutdown.
- **Build and deploy.** `tsup` bundles to `dist/{bot,worker,migrate}.js`; multi-
  stage `Dockerfile`; `compose.yaml` with postgres, redis, a one-shot `migrate`
  service, bot and worker; explicit `pnpm db:migrate`.
- **Tests.** 52 total (up from 30): settings persistence across reopen, JSONB
  fidelity, module isolation, migration idempotency, atomic cooldowns, retry
  exactly-once, terminal failure, duplicate delivery, trace parentage, `/setup`
  readiness branches, and one integration test spanning command → DB → queue.
- **Docs.** [[ADR-0006-ports-and-adapters]], [[Master-Plan|master plan]] phase
  evidence, [[04-Modules/setup/Spec|setup spec]]/[[04-Modules/setup/Status|status]]/[[04-Modules/setup/Teaching|teaching]], [[Redis]] runbook.

## What we tried and rejected

- **Importing Drizzle/Redis directly where needed.** Fastest to write and would
  have put a database client in every module within two phases. Rejected; the
  ports are the promise P0 made. ADR-0006.
- **A repository per table in the kernel.** More types, same coupling; the kernel
  would depend on Postgres. Rejected in favour of one settings repository and
  module-owned services later.
- **Requiring Redis to boot.** Cleaner consistency story, but local development
  and the token-free suite would need a server. Rejected: unset variables select
  a *logged* local mode; a configured-but-unreachable service still fails boot.
- **Running migrations on boot.** Convenient and wrong: two replicas race, and a
  failed migration leaves a half-started bot. Rejected for a one-shot migrate
  service and `pnpm db:migrate`.
- **Leaving runtime dependencies external in the bundle.** The first build
  succeeded but the artefact could not resolve `postgres` or `discord.js` because
  pnpm does not hoist to the root. Rejected; bundled everything except PGlite,
  with a `createRequire` banner for CJS dynamic requires.
- **Editing migration 0001 to drop NOT NULL.** Two databases with the same
  version would disagree. Added `0002_settings_nullable` instead.
- **Making the settings value a `text` column.** It would have dodged the JSONB
  driver differences and broken the plan's `(module, key, jsonb)` spine. Rejected;
  the adapter reads `::text` and parses exactly once.
- **Loosening the null/`"123"` assertions.** They were real bugs: Drizzle sends
  `null` as SQL NULL, and PGlite returns parsed JSON that Drizzle would re-parse.
  Both fixed in the adapter; the assertions stayed.
- **A Components V2 `/setup` panel now.** Deferred to P3 with `packages/ui`:
  defer-then-edit and the 40-slot budgeter do not exist yet, and the plan forbids
  spending component budget before the budgeter. `/setup` ships as an embed.
- **Using BullMQ's `jobId` as the whole idempotency story.** `jobId` dedupes while
  the job exists; it says nothing after completion. Rejected; Postgres receipts
  record completion, and a redelivered completed job is skipped.

What is proven:

- Settings written through the port survive close-and-reopen against PGlite (the
  real Postgres engine as WASM) with nested objects, null, numbers, unicode,
  arrays and a numeric-looking string intact; module keys do not leak.
- 50 concurrent cooldown hits produce exactly one winner; TTL expiry lets the
  next caller through; the fallback warns and is process-local.
- A transiently failing job retries, applies its side effect once, and ends
  `completed`; a permanently failing job stops at three attempts and is recorded
  `failed`; a duplicate delivery after completion is skipped.
- One trace id covers `command`, `db.settings.get`, `db.settings.set`,
  `queue.enqueue` and `job demo.job`, with correct parent span ids.
- The built artefacts are self-contained and fail with the intended messages.

What is **not** proven here, and is named rather than asserted:

- **Live BullMQ retry.** No Docker daemon, Postgres or Redis binary exists in
  this environment, and the WSL user cannot install one. The BullMQ adapter's
  connection parsing, retry policy and job-id mapping are unit-tested; the retry
  behaviour itself is proven on `InProcessJobQueue`, which shares the policy.
  Confirming it needs `docker compose up redis` and a worker run.
- **A live gateway login.** No token, and no `.env`.
- **The Docker image.** The Dockerfile and compose file are written but could not
  be built or started without a daemon.

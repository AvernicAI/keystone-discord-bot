# Pass 29 — guild analytics

**Date:** 2026-11-01 · **Phase:** P7 · **Branch:** main

## Why this pass

The plan names `/analytics` as the next missing root. Carl-bot and Wick sell
server insights, and the bot now owns enough real ledgers — audit events, cases,
invite joins, tickets — for an overview to be useful without inventing metrics.
This pass deliberately adds **no new collection path**: every number is a query
over rows another module already writes.

## What changed

- New `modules/analytics` package: manifest, settings schema, six views, an
  embed formatter, an in-memory aggregation adapter, command tests and a
  PGlite adapter test.
- `/analytics overview | members | messages | commands | tickets | export` under
  one new root. The ledger is now **14 roots · 90 subcommands · 104 actions**.
  `days` is bounded 1–90 and defaults to the module setting (7).
- New `command_usage` table and `DrizzleCommandUsageStore`; migration `0010`.
  One append-only row per dispatched guild command, written **after** the
  command finishes so status and duration are real. Dispatch records it through
  an optional `usage` port; a failed recording never turns a successful command
  into an error.
- `packages/kernel/src/analytics.ts` owns the read model and the one
  `AnalyticsStore` port. There is no analytics table and no second counter to
  reconcile.
- `DrizzleAnalyticsStore` aggregates with SQL. `MemoryAnalyticsStore` aggregates
  the same records from the in-memory stores the gateway already uses, so local
  mode is truthful instead of returning zeros.
- In-memory stores gained read-only `records()`/`tickets()` helpers; they are
  adapters for analytics, not a second state owner. The production path reads
  SQL.
- Analytics is admin-only (`ManageGuild`), guild-scoped, read-only and has a
  three-second cooldown. No new intent, permission or paid service was added.

## What we tried and rejected

- **A new analytics event table.** Rejected: it would duplicate five ledgers and
  make every printed number a chance to drift. Queries over the source rows are
  the only version we can cross-check.
- **Incrementing counters on each event.** Rejected for the same reason. A
  counter cannot be audited against the rows it claims to describe, and a missed
  increment is invisible forever.
- **Counting every message, not just logged ones.** Rejected: the bot does not
  store unlogged messages, so such a number would be fiction. `/analytics
  messages` says it counts logged events and names the toggles that create
  coverage.
- **A public dashboard analytics endpoint in this pass.** Rejected: the root is
  already the product surface; adding a web read path would widen the P6 auth
  surface without a requested screen. The same `AnalyticsStore` can be wired
  later behind the existing guild gate.
- **Reading message content into analytics.** Rejected: aggregates never need
  content, and the export explicitly excludes it.
- **Treating open tickets and active cases as window counts.** Rejected: those are
  current state, so the page and command say so. The other figures use the
  selected window.
- **An in-memory-only implementation.** Rejected: it would prove the command but
  not the Postgres path. The PGlite test builds real rows through the existing
  stores and compares the snapshot to raw `count(*)`.

The cross-check is direct:

- `!logging status` read **2 stored** audit rows; `/analytics overview` printed
  **2 logged events** for the same window. The figure is the ledger, not a
  parallel count.
- One MCP edit and one MCP delete produced exactly **1 edited** and **1
  deleted** in `/analytics messages`; no other message events existed.
- The command count rose **0 → 3 → 4** as bridge commands completed. The current
  `/analytics` run is recorded after its reply, so it appears in the next call —
  the observed increment is the dispatch ledger behaving as documented.
- `pnpm commands:doctor` after boot reported `Registry 14 roots · 90
  subcommands` and `Discord 14 global chat-input commands · 90 subcommands`,
  with `analytics` in the names list.

The MCP text reader does not render embeds, so the live transcript proves the
plain-text summary. The embed fields, the top-command list and the JSON export
are covered by the command test; a human slash run still renders them.

## Next

- Wire the same `AnalyticsStore` into a dashboard page behind the existing guild
  gate, when a screen is actually requested.
- Add a member-movement proof with a real join/leave; member analytics currently
  reads adapter-tested audit rows and invite records.
- Add retention-aware growth charts only after the ledger has enough history;
  a chart over three rows would be decoration.
- Keep the command ledger append-only and prune it with a documented window
  before it becomes large enough to matter.

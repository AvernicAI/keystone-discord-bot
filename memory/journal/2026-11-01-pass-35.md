## What changed

`/appeal` was a root with two options and one effect: append an `appealed` event.
It is now a two-subcommand hub:

| Subcommand | Options | Behaviour |
| --- | --- | --- |
| `/appeal open` | `case` (required), `message` | Same target-only guard; appends the existing `appealed` event and sets the case state to `appealed`. Never reverses automatically. |
| `/appeal status` | optional `case` | Reads the append-only `appealed` events for the caller's cases and prints the current case state beside the appeal count. With `case`, shows one case and refuses a case that is not the caller's. |

The new seam is `CaseStore.listEvents(caseId)`, implemented by:

- `modules/moderation/src/cases.ts` — the in-memory store returns a copy of the
  event list; `CaseService.listEvents` is the port method commands use.
- `packages/db/src/case-store.ts` — `DrizzleCaseStore` selects `case_events` by
  `caseId`, ordered by `createdAt, id`, so the append-only rows are the source.
- `packages/kernel/src/types.ts` — `CaseStore` and `CaseServicePort` declare the
  method. No new table, migration or module.

`modules/moderation/src/format.ts` adds `appealStatusEmbed`, which renders each
entry with its case number, action, current state, appeal count, last filed time
and the last appeal message (capped at 500 characters). The command also sends a
plain-text summary because the MCP reader cannot render embeds; that text is what
the live transcript below reads back.

The root keeps its global slot and gains two real subcommands. It has a 5-second
cooldown, remains guild-only and has no new permission. `open` still respects
`appealsEnabled`; `status` is a read and works even if appeals are later disabled.

### The cross-check

The claim is not "the command remembers". It is that the number comes from the
append-only rows:

- `!mod warn` opened case **#1** with one `created` event.
- `!appeal open case=1` appended one `appealed` event with the supplied message.
- `!mod review case=1` appended a `reviewed` event and changed `cases.state` to
  `reviewed`; it did not delete the appeal.
- `!appeal status case=1` then printed **1 appeal** while the state line changed
  from `appealed` to `reviewed`. The only way status can know that is
  `CaseStore.listEvents`, which reads the event rows, not the state column.
- `!appeal status` scanned the caller's ten newest cases; case #2 (target: the
  bot) had no appeal event, so the output still contained only case #1.
- `Case #2 is not one of your cases.` came from the ownership filter before any
  event read, so another member's case number is not disclosed.
- The PGlite test `packages/db/src/cases.test.ts` asserts
  `DrizzleCaseStore.listEvents` returns the appended `appealed` event, which is
  the SQL counterpart of the in-memory rows used live.

### What the MCP author could not trigger

- **A human slash invocation.** The MCP cannot call application commands; the
  bridge proves the same registry, guards and handler, not `InteractionCreate`.
  A human `/appeal open` and `/appeal status` remain the unobserved surface.
- **Embed rendering.** The MCP text reader does not render embeds. The command
  therefore sends a plain-text summary in addition to the embed; the fields and
  the 500-character message cap are covered by `mod.test.ts`, not read live.
- **A second human member.** The ownership refusal was proven with a case against
  the bot, not another human. The unit test uses a second fake member for the
  same path.
- **A human-authored moderation case.** The MCP author was both moderator and
  target. The case and appeal rows are real, but the actor is the MCP bot.
- **Disabled appeals and a closed case.** Both are covered by command/service
  tests; neither was exercised in the live window.
- **SQL live.** Local Postgres still returns `ECONNREFUSED`; the event query is
  proven by the PGlite test, not by a live database.

## What we tried and rejected

- **A separate `appeals` table.** Rejected. `case_events` already stores
  `appealed` with the message and timestamp, and the case file is append-only by
  design. A second table would duplicate the same fact and could disagree.
- **Deriving appeal status from `cases.state`.** Rejected. A moderator's review
  changes the state, so status would silently forget the appeal. The live proof
  exists specifically to catch that mistake.
- **Keeping the old root options and adding subcommands beside them.** Rejected.
  Discord does not allow a command to have both root options and subcommands,
  and two spellings of the same action are a migration trap.
- **Shipping `/verify start | status` in the same pass.** Rejected by the
  single-root scope. It is the next named gap and needs a different fixture.
- **Inventing the two missing `/verify` names or the rest of 160.** Rejected;
  the table above names only what exists.

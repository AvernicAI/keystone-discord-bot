# Pass 22 — dashboard server boundaries

**Date:** 2026-11-01
**Phase:** P7 maintenance (P6 dashboard surface)
**Commit:** pending (working tree)

## What changed

`apps/web/src/server.ts` had become the whole web process: an ordered route
table, all HTML and CSS, cookie handling, body parsing, session lookup, token
decryption, guild authorization, CSRF checks and every handler. The guild-id
regex was written four times. The settings POST and PATCH handlers repeated the
same authorization and CSRF sequence.

This pass is a pure restructure. Routes, status codes, headers, bodies and the
existing `web.test.ts` contract are unchanged.

### The new responsibility map

| File | Owns |
| --- | --- |
| `server.ts` | Security headers, error boundary, request context, dispatch, final 405/404 |
| `routes/index.ts` | The one ordered route table and shared guild/module patterns |
| `routes/auth.ts` | Health, login, OAuth callback, logout and landing |
| `routes/dashboard.ts` | Guild list, guild overview, settings editor and form save |
| `routes/api.ts` | `/api/v1` reads, settings `PATCH` and the API 404 |
| `request-context.ts` | Web dependencies, cookie parsing and the one session lookup |
| `authorization.ts` | Session check, guild authorization, and the one settings-write/CSRF gate |
| `http.ts` | Response helpers, CSP headers, body parsing and settings parsers |
| `render.ts` | Layout, escaping and every HTML page renderer |

The route table is the only place that decides matching order. `requireSettingsWrite`
is the only place that decides the sequence for a guild settings write:
session -> guild authorization -> token read -> CSRF check. Both the HTML form
and the API call it once.

The two rules that mattered during the move:

1. **Order is behavior.** The settings page authorizes an unsupported method
   before falling through to the 405 fallback, and the form parses its body as
   part of reading its CSRF token. Both orders are preserved.
2. **One session read.** `createRouteContext` resolves the opaque cookie to a
   `WebSession` once per request; handlers never re-parse cookies or re-hash the
   session id.

### A defect caught by the contract

The first extraction of the shared route pattern removed the capturing
parentheses from the guild-id and module-id fragments. The route matched, but
`params` was empty; every guild-scoped request reached authorization with
`undefined` and returned `403`. The real web test caught it before any docs were
written. The shared constants now include the captures, and the web contract is
green again. This is exactly why the refactor did not start with a new router
abstraction.

## What we tried and rejected

- **Keep the handlers in `server.ts` and only extract `render.ts`.** Rejected:
  the authorization duplication and the route table would remain entangled with
  the error boundary.
- **A third-party router or framework.** Rejected: it would change error,
  method and API fallback semantics for a 12-route surface, and the repo is
  deliberately framework-free.
- **One module per route.** Rejected as ceremony. Auth, dashboard and API are
  three natural areas; splitting each exact route would add files without a
  boundary.
- **A second settings-write helper for the API and the form.** Rejected: the
  whole point is one gate; the callback lets each surface read its own token
  while preserving order.
- **Adding a new route or feature.** None. No response shape, status code,
  header or test meaning changed.

## Limits

- A live Discord OAuth round trip and a Postgres-backed session are still not
  claimed; the tests use a real local HTTP server with a fake OAuth port.
- The dashboard remains server-rendered HTML plus `/api/v1`; this pass does not
  add field widgets, fleet actions or scoped API tokens.
- The route table is hand-written by design. A route added without a table entry
  will fall through to the 405/404 path; there is no decorator or file scanning.

## Next

- Add the next P6 capability (schema-driven field widgets or fleet reads) as a
  new handler plus one table entry, not as another branch in `server.ts`.
- Keep the write gate as the only settings-write entry point.

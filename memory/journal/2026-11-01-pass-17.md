# Pass 17 — P6 dashboard/API foundation

## What changed

- Added `apps/web`, an optional Node HTTP service that proves the P6
  authorization boundary before any UI framework or write surface exists:
  - Discord OAuth2 authorization code + PKCE, sealed state cookie, `iss` and
    redirect-URI validation.
  - Opaque server-side sessions. The browser holds a random value; Postgres holds
    only its SHA-256 hash. Discord access/refresh tokens are AES-256-GCM sealed
    before storage and never returned by a route.
  - `GuildAccessService`: owner/`ADMINISTRATOR`/`MANAGE_GUILD` parsed with
    `BigInt` **and** a bot-token membership check. A URL guild id is never
    trusted. Bit 40 (`MODERATE_MEMBERS`) is explicitly tested not to imply
    Manage Guild.
  - Read-only HTML dashboard (`/dashboard`, `/dashboard/guilds/:id`) and
    `/api/v1/me`, `/api/v1/guilds`, `/api/v1/guilds/:id/overview`.
  - Strict CSP, `X-Frame-Options`, `Referrer-Policy`, `no-store`, escaped HTML
    and no secret in the JSON health response.
- Added kernel ports `SessionStore`, `DashboardStore` and `WebSession`; Postgres
  adapters `DrizzleSessionStore` and `DrizzleDashboardStore`; migration `0006`
  for `web_sessions`. The dashboard reads settings through the existing
  `SettingsService`, not ad-hoc SQL.
- Added `packages/module-catalog` so the bot and dashboard share one module list.
- Added `web` to the tsup build, an optional compose `web` service, root
  `pnpm web:start`/`web:dev` scripts, `.env.example` P6 placeholders and the
  README/Dashboard/ADR documentation.
- Recorded the permanent rule: **no paid GitHub plan/feature and no other paid
  service**. The project stays on public GitHub, Discord, local Postgres/Redis/
  Ollama, PGlite and in-memory adapters.

## What we tried and rejected

- **Next.js first.** Rejected for this pass: a framework and client bundle would
  have hidden the actual risk (the authz matrix) behind more moving parts. The
  plain HTTP handler made the rejection tests cheap and exact. ADR-0016 records
  the trade-off; a Next.js shell can consume the same services later.
- **JWT-only sessions.** Rejected: a demoted guild admin would keep access until
  expiry. The opaque session is revoked immediately on logout and expiry.
- **Discord token in the browser.** Rejected: one XSS would become a seven-day
  account takeover. Tokens are sealed server-side; tests assert neither the HTML
  nor JSON contains them.
- **Trusting the OAuth guild list alone.** Rejected: the `:guildId` URL would be
  an IDOR. Every guild route also checks bot membership.
- **A dashboard query helper with raw SQL in `server.ts`.** Rejected: it would
  duplicate the P5 data model and bypass the ports. Reads go through
  `SettingsService` and `DashboardStore`.
- **Building settings writes first.** Rejected: the roadmap's kill signal says
  read-only first when the authz matrix is not proven. Writes, 2FA/step-up and
  sub-resource checks stay open.
- **Clearing the command set again.** Not needed: no command root or payload
  changed in this pass; the bot surface remains 10/100.

port. No test needs Discord, a database server or a network call. The live

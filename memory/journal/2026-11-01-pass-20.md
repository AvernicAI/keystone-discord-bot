# Pass 20 — cold-cache attribution, session cleanup and memory corrections

**Date:** 2026-11-01
**Phase:** P7 invite fix and P6 cleanup
**Commit:** `fix(invites, web, memory): make cold-cache attribution honest and remove unused session refresh state`

## What changed

### Invite attribution has an explicit cold-cache path

`registerInviteEvents` used to call:

```ts
const before = caches.get(guildId) ?? new Map();
```

An absent cache therefore became an empty baseline, and `attributeInvite` treated
every existing invite's historical `uses` total as a fresh increment. The first
join after ready, or after a transient refresh failure, could be attributed to
the most-used invite rather than the invite that was actually redeemed.

The adapter now reads the cache without a fallback and only diffs when a baseline
exists:

```ts
const baseline = caches.get(guildId);
const attribution =
  baseline && after ? attributeInvite([...baseline.values()], [...after.values()]) : undefined;
```

A cold-cache join is recorded with no inviter, and the fresh fetch seeds the cache
for the next join. That is “unknown,” not a guess. The new adapter test uses a
fake gateway client and a store spy; it failed before the fix with
`{ code: "popular", inviterId: "inviter-a" }` and passes after with neither field.
The pure-function tests still cover increment, new-code, unchanged and tie cases.

### No unused Discord refresh token is stored

P6 accepted an authorization-code token response, sealed the refresh token into
`web_sessions`, and never used it. There is no refresh grant, no per-session
single-flight lock and no rotation path, so the stored credential was pure risk
and made the session look more capable than it was.

The pass removes that illusion instead of adding a half-built refresh feature:

- `WebSession` and `SessionStore` no longer carry `refreshToken` or `rotatedAt`.
- `SessionStore.update` and the `SessionPatch` type are gone; nothing used them.
- `OAuthTokens`, `DiscordOAuthOptions`, `DiscordOAuthClient` and `AuthService`
  no longer accept or return a refresh token, `expiresIn` or an unused `issuer`
  getter.
- Migration `0008_web_session_cleanup` drops `refresh_token` and `rotated_at`
  from `web_sessions`.
- The session keeps only the sealed access token, its CSRF hash, creation time
  and expiry. At expiry the user signs in again. Discord's access-token lifetime
  is seven days; the session TTL is the same seven days.

The focused web/PGlite suites still cover login, CSRF, guild scoping, no-token
responses and the session round trip without refresh credentials.

### Memory matches the code again

- The Status and Roadmap pages no longer claim the ready path clears and
  re-registers commands every boot. It fetches the command set and only clears
  when the names drift; `pnpm commands:resync` is the explicit cycle.
- The MEE6 invite claim now matches the cited wiki: the tracker is partly
  premium-gated (“certain parts or the entirety … may require a Premium
  Subscription”), not a separately sold plugin. The Matrix no longer attributes
  an “only its own invites” rule the wiki does not state.
- The P7 acceptance table now records the cold-cache adapter test and says the
  per-guild serialization is code-inspected, not backed by a dedicated race test.
- The generated feature status gets the adapter test as evidence for invite
  attribution.

## Why this shape, not a refresh implementation

Refresh would need a refresh grant, access-token expiry persisted per session, a
per-session single-flight lock, rotation, 401-to-refresh recovery and tests for
all of it. That is a real P6 feature, not a defect fix. Removing the unused
credential is smaller, makes the current seven-day session behavior honest, and
leaves the refresh decision to a pass that can test the whole path. Storing a
refresh token “for later” was the original mistake.

## What we tried and rejected

- **Diffing historical totals on a cold cache and calling the largest one the
  winner.** Rejected: it silently assigns a wrong inviter; an absent baseline is
  not a baseline of zero.
- **Keeping the refresh columns and fields for a future feature.** Rejected: an
  unused long-lived credential at rest is a liability, and dead fields made the
  session contract harder to read.
- **Implementing refresh in this pass.** Rejected as scope and risk: it needs
  expiry persistence, rotation and single-flight, not just another field.
- **Editing the old migration to remove the columns.** Rejected: applied
  migrations are historical; the ordered `0008` migration is the safe change.
- **A new command, setting or dashboard screen.** None; this pass changes
  existing behavior and removes code.

## Limits

- A live member join is still unperformed; the adapter regression test uses a
  fake gateway client and proves the cold-cache branch without Discord.
- The per-guild serialization still has no dedicated race test; it is code
  inspected and the SQL join key remains the idempotency backstop.
- No refresh path exists. The session TTL matches Discord's seven-day access
  token, and the user re-authenticates after it expires.
- Migration `0008` is PGlite-tested; no live Postgres migration was run.

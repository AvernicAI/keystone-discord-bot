# Pass 84 — The case card joins the grammar, the dashboard picks real channels

## What changed

**The case card is a panel, not three embeds.** `modules/moderation/src/format.ts`
had three hand-written embed builders and a legacy `ActionRow` for the appeal
button, drawn from twelve call sites. It is now three builders on the shared
grammar, with no embed and no raw hex in the file:

- `casePanel(record, options)` — accent by state (`attention` for
  pending/open/alerted/appealed, `brand` for reviewed, `muted` for
  reversed/closed), `heading({ glyph: GLYPHS.shield, title: "Case #42 · ban" })`,
  one `facts` line (target, actor, state, `<t:…:R>` expiry), a clipped `Reason`
  block, a `footer` with `readStamp` and "events are append-only", a dry-run
  sentence when the action was a preview, and exactly one `actionRow` **inside**
  the container. Options: `appealId`, `verifyId`, `title`, `context`, `accent`,
  `dryRun`, `note`, `readAt`.
- `caseListPanel(records, title, { readAt })` — state counts on the facts line,
  up to twelve `row()`s with relative timestamps and `source: "cases"`, a
  `+N older not shown.` line, a read stamp, and an empty state that names
  `/mod warn`.
- `appealStatusPanel(entries, title, { readAt })` — rows read from `case_events`
  with the message excerpt and the same read stamp; the empty state names
  `/appeal open case:<n>`.

The builders are now the only way a case is drawn: `/mod case`, every `/mod`
action reply, `/mod history`, `/mod review`, `/mod note`, the case-history user
menu, `/appeal open`, `/appeal status`, the report-message confirmation, the
security alert and the temporary-action release all call one of them. The three
embed builders and `appealStatusEmbed` are deleted. `accents` still come from
`@keystone/ui`; `tokens` flips to `enforced` in the surface ledger.

`actionRow` allows one primary, so a join-gate case shows **Verify and join** as
primary and steps **Appeal this case** down to secondary. A case with only the
appeal keeps it primary. No new button id was introduced; the ids are the same
signed `appeal:open`/`verify:complete` values the router already verifies.

**A notice can now carry a card.** `ModerationNotice` gained
`v2?: readonly V2Component[]`, documented as mutually exclusive with `embeds`
and `components` in the same words as `CommunityMessage`.
`apps/bot/src/adapt.ts` gained `toChannelMessage(notice)`, which is the only
place that knows `MessageFlags.IsComponentsV2`; the kernel still imports no
discord.js. `ModerationActions.notify` sends through it, so the mod-log message
can be the same card a moderator sees instead of a second renderer in a second
package. A unit test feeds both shapes through the adapter: the V2 notice gets
the flag and no content/embeds, and an embed-only caller keeps the legacy shape.

**The settings editor reads the server.** `SettingsField` gained
`reference?: "channel" | "role"`, derived from the last key segment
(`…ChannelId`/`…RoleId`). A comma-separated list such as `djRoleIds` is
deliberately not a reference: a single-value control would silently drop entries.
When the page process has the `DirectoryPort` (the bot token is configured),
`referenceChoices` turns the cached read into options grouped by category with
type glyphs — `# general`, `🔊 Lounge`, `@Moderator` — and omits managed roles,
because Discord rejects assigning them. A stored id that the current read does
not contain stays **selected and labelled** (`⚠ <id> · not in this server`) so
the next unrelated save cannot erase it. Without a read, or when the read fails
(403/404/429/503), the field stays a text input and a sentence names the
Directory page and the reason; the ids remain editable. No schema changed, so the
bot still validates the same strings.

## What the gate caught

- `pnpm typecheck` caught a duplicate `GuildDirectory` import in `render.ts` and
  an unhelpful `.toJSON()` on a union of discord.js component data in the new
  adapter test. Both fixed at the cause; no cast was added to the production
  code.
- The full suite caught `apps/bot/src/interaction-harness.test.ts` still
  asserting the old `Case #1 recorded and action applied.` content string. That
  test crosses the real adapter, registry and dispatch, so it was right to fail:
  the reply is now a V2 payload. It asserts `IsComponentsV2`, no content, and the
  card's own copy.
- The picker test fixture initially required a `logging` object in a schema that
  made it optional; the test schema now mirrors the real one with `.default({})`.

## What is proven, and what is not

Proven by tests (token-free): the three panels' structure (accent, facts, reason,
read stamp, one action row, no second primary, list caps, empty states), the
adapter's flag/exclusivity rules for both shapes, the picker metadata, category
grouping, `@everyone` versus managed roles, the preserved unknown id, the
text fallback, and one real settings-page request through the web harness with a
fake directory (select with `optgroup`) and without one (text input plus the
note).

**Not proven:** nobody has opened a case card in Discord. This run had no
gateway interaction and the MCP cannot invoke a slash command, so the surface
stays graded **B** with `proof: null` rather than an A. That means the visual
result — spacing, how the accent reads, whether the footer wraps — is unverified
even though the payload is.

## What we tried and rejected

- **Keeping the embeds behind a compatibility branch.** The notice port already
  carries `v2`; a second path would be a second renderer to keep in sync, which
  is the defect this pass removes.
- **Putting `MessageFlags` in the kernel to "simplify" notify.** It would import
  discord.js into the layer that runs in the worker and tests without a token.
- **Sending `v2` and `embeds` together and letting Discord choose.** Discord
  rejects the payload; the adapter now deletes content/embeds for the V2 path.
- **Auto-clearing a stored channel id that is not in the directory read.** It
  hides a broken reference and makes the next save destructive.
- **A picker for every `…Ids` list.** Only single-id keys get one.
- **Rendering the picker as a `<datalist>`.** It allows arbitrary text while
  looking like a closed list; a `<select>` with an explicit "not in this server"
  option tells the truth.
- **Reading the directory on every keystroke or on the POST.** The read is on
  GET (cached 60 s by the port) and a failure degrades to text; the submission
  path never depends on Discord being reachable.

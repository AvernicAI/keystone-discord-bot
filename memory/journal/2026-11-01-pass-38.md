# Pass 38 — Button rules leave the composition root

**Date:** 2026-11-01
**Phase:** P7
**Tree before:** `d74bc93` (clean) · 17 roots / 117 subcommands / 134 actions / 4 context menus / 385 tests
**Tree after:** this pass · same ledger · 398 tests / 59 files

## The debt

`apps/bot/src/index.ts` was 348 lines. Besides composition, it held the whole
appeal/verify button path inline inside a second `InteractionCreate` listener:
prefix matching, `keystone:appeal:` slicing, the two shapes of
`keystone:verify:` ids, the legacy guild fallback, the DM-vs-guild ephemeral
rule, the wrong-actor refusal, two settings reads, the completion call and both
error fallbacks. None of it could be exercised without constructing a gateway
interaction, and the parsing rules sat four imports away from the runtime they
mutated.

## What changed

`apps/bot/src/moderation-buttons.ts` now owns that path:

- `parseModerationButtonId(customId, interactionGuildId)` returns an appeal
  route, a current `keystone:verify:<guildId>:<userId>` route, or a legacy
  `keystone:verify:<userId>` route that borrows the interaction's guild. Empty
  segments, a legacy id with no guild and a foreign prefix return `undefined`.
- `handleAppealButton` keeps the same settings read, `appealsEnabled` refusal,
  `cases.appealById` call and exact reply strings.
- `handleVerifyButton` keeps the encoded-user identity check before any settings
  or store read, the `ephemeral = guildId !== null` rule, and the shared
  `completeVerification` call.
- `handleModerationButton` dispatches by route and returns `false` for ids it
  does not own.

The handler accepts a structural `ButtonInteractionLike`
(`customId`, `guildId`, `userId`, `reply`), so the tests need no discord.js and
`index.ts` remains the only file that sees a gateway interaction. `toReplyOptions`
is exported from `adapt.ts` so the button replies use the same conversion as
every command reply.

`apps/bot/src/index.ts` is now **287 lines**, down from **348**. Its listener is
eight lines: map the four fields, call the handler, log a rejected promise. No
command, menu, reply string, registration or ledger count changed.

## Behavior notes

- The reply strings are byte-for-byte the inline versions. The appeal flow still
  refuses a disabled `appealsEnabled` before touching a case; the case service
  still owns the target-only rule.
- These buttons are **member-facing**. There is no staff permission check to
  preserve or add: the authorization boundaries are the encoded user id, the
  operator's appeal/join-gate settings, and the case service's target check. The
  refactor does not invent a Discord permission gate.
- One stricter parse: a verify id with more than two segments used to fall
  through to the legacy form and treat its first segment as a user id. No real
  button has that shape (`verifyCustomId` always emits two segments), so it is
  now rejected as malformed rather than guessed at. Every id the bot actually
  creates parses exactly as before.
- The DM port (`ctx.community.actions.sendDM` in
  `modules/moderation/src/commands/verify.ts`) did not move. That remains the
  last deferred audit finding.

## What we tried and rejected

- **Import discord.js into the handler module.** Rejected: it would make the
  parsing rules depend on a gateway type and force a fake client into the tests.
  The structural interface keeps the adapter thin.
- **Keep the listener in `index.ts` and only export the parser.** Rejected: the
  settings reads and completion call would still be untestable composition, and
  the pass exists to remove exactly that.
- **Add a `ModerateMembers` guard to the buttons.** Rejected: that changes the
  product. These are member-facing appeal and verify buttons; a staff gate would
  lock members out of their own cases and verification.
- **Build a generic button router for every prefix.** Rejected as premature:
  community, roles, tickets and polls already have their own event adapter, and
  a second shared router would duplicate that surface for two buttons.
- **Move the DM port in the same pass.** Deliberately deferred; the request
  keeps it separate, and mixing a module-layer move into an adapter refactor
  would make the diff harder to review.
- **Change the reply text while it was open.** Rejected. A refactor that also
  edits copy cannot prove the copy did not change.

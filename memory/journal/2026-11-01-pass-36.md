## What changed

`/verify` was an optionless root that removed the quarantine role. It is now a
hub:

| Subcommand | Options | Behaviour |
| --- | --- | --- |
| `/verify start` | none | Requires the join gate, rejects an already-verified member, rejects a record that is not quarantined, then sends the existing verification button by DM. A closed DM is an explicit refusal. |
| `/verify status` | none | Reads the persisted `members` row and reports the join-gate setting, quarantine flag, join time and next step. The footer names the table; gateway roles are not consulted. |

The new seam is `MemberStore`, a narrow port over the `members` table that
already existed for portability:

- `packages/kernel/src/types.ts` — `MemberVerification`, `MemberStore`, and
  `ModerationPort.members`.
- `modules/moderation/src/members.ts` — the in-memory implementation. It is a
  real upsert on the same contract, not a stub.
- `packages/db/src/member-store.ts` — `DrizzleMemberStore`. `get` selects one
  `(guild_id, user_id)` row; `markVerified` inserts or updates it, clears
  `quarantined`, preserves the original `joined_at`, and advances `verified_at`.
  No migration was needed.
- `modules/moderation/src/verification.ts` — `completeVerification`, the single
  completion path. It checks the actor, the gate setting and `verified_at`, calls
  the existing `unquarantine` action, and only then writes the row. If Discord
  fails, no row is written.
- `apps/bot/src/index.ts` — the DM and legacy in-guild buttons both call the same
  function. The custom id now carries the guild id so the button works outside a
  guild context; the one-part legacy form still falls back to the interaction's
  guild.
- `apps/bot/src/runtime.ts` — the composition root chooses `DrizzleMemberStore`
  when `DATABASE_URL` is configured and `InMemoryMemberStore` otherwise.

Why a port instead of reading `members` in the command? The command must work in
both local mode and Postgres without knowing which one is live, and the existing
`ModerationPort` is the established seam for the module. The table was already in
the schema, so no migration or parallel store was invented.

`start` is deliberately **not** the completion. It answers "can this member
actually complete the flow now?" and sends the button. `status` is deliberately
**not** derived from gateway roles: it reads the row, so a role rename or a
manual role edit cannot make the bot claim a verification that never happened.

## What we tried and rejected

- **Read `members` directly in the command.** Rejected: it would couple the
  module to Drizzle and break the local-mode composition. The existing
  `ModerationPort.members` seam costs one small port.
- **Mark the member verified in `start`.** Rejected: a command would then claim a
  verification even when the DM or the role removal failed. The button remains
  the only completion path, and the row is written after `unquarantine` succeeds.
- **Derive status from the quarantine role.** Rejected: a role rename, a manual
  grant or a permission change would change the answer without a row changing.
  The persisted row is the source of truth; the command's footer says so.
- **Add a migration for a new verification table.** Not needed: `members`
  already had `joined_at`, `quarantined` and `verified_at`. A second table would
  have split portability and the join gate.
- **Use the legacy one-part button id.** Kept as a fallback, but new buttons carry
  the guild id so a DM button is unambiguous. The handler accepts both.
- **Leave `/verify` optionless as a "fallback".** Rejected: the saved plan names
  `start` and `status`, and an optionless root would keep two real commands
  hidden behind a default action.
